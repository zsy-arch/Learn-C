# 03_sorting —— 六种排序的完整对比

## 实验目的

回答新手的四个真实困惑：

1. 冒泡/选择/插入都是 O(n²)，为什么插入排序实际上快那么多？
2. 归并排序「稳定」到底是什么意思？怎么用代码证明？
3. 快排的「最坏情况」是真实存在的吗？
4. 小数据量下，O(n²) 会不会比 O(n log n) 快？

## 算法总览

| 算法 | 平均 | 最坏 | 空间 | 稳定 | 原地 | 特点 |
|---|---|:---:|:---:|:---:|:---:|---|
| 冒泡 | O(n²) | O(n²) | O(1) | ✅ | ✅ | 已排序时 O(n)，教学用 |
| 选择 | O(n²) | O(n²) | O(1) | ❌ | ✅ | **交换次数最少**（≤ n-1） |
| 插入 | O(n²) | O(n²) | O(1) | ✅ | ✅ | 近乎有序时接近 O(n) |
| 希尔 | O(n^1.5) | O(n^1.5) | O(1) | ❌ | ✅ | 插入排序的改进 |
| 快速 | O(n log n) | **O(n²)** | O(log n) | ❌ | ✅ | 平均最快，但最坏会退化 |
| 归并 | O(n log n) | O(n log n) | **O(n)** | ✅ | ❌ | 稳定，最坏也是 O(n log n) |

## 2. 稳定性：怎么测才有效

**测试稳定性必须满足两个条件**：

1. 存在**真正相等**的元素（比较时「看不出区别」）
2. 元素身上带着能区分原始顺序的**额外信息**

> **踩过的坑**：最初想把 key 和 id 编码进一个整数（`key * 1000 + id`）来省事。
> 结果比较的是整个编码值，id 也参与了比较，于是**所有元素互不相等**，
> 任何算法看起来都「稳定」—— 这个测试就完全无效了。
>
> 正确做法：用 `struct { int key, id; }`，比较时**只看 key**。

```text
========== 2. 稳定性：逐算法实测 ==========
  原始 (key#id) 0#4 0#3 0#2 0#1 0#0 1#4 1#3 1#2 1#1 1#0 2#4 2#3 2#2 2#1 2#0 3#4 3#3 3#2 3#1 3#0 

  bubble     稳定
  selection  稳定     ← 这组数据太规律，凑巧没暴露问题
  insertion  稳定
  quick      不稳定   ← 0#0 跑到了 0#4 前面
  merge      稳定

  ---- 选择排序的最小反例（3 个元素）----
  原始         2#0 2#1 1#2 
  选择排序后 1#2 2#1 2#0 
                   ^ 两个 key=2 的元素，id 从 0,1 变成了 1,0 —— 顺序被交换了！
  原因：第一轮找到最小值 1（在下标 2），把它和下标 0 交换。
        下标 0 上的 2#0 被扔到了下标 2，跨过了 2#1。
```

**注意「selection 稳定」这一行**：第一组数据太规律，选择排序**凑巧**保持了稳定。
三元素反例才是不稳定的真正证明。**这就是为什么测试数据要精心设计。**

不稳定的根本原因：**跨越式交换**。

```text
  下标:   0     1     2
        2#0   2#1   1#2
          \           /
           \         /
            └─ 交换 ─┘        ← 2#0 被跨过了 2#1

  结果:  1#2   2#1   2#0      ← 两个 2 的顺序反了
```

## 3. 操作次数

```text
========== 3. 操作次数对比（n = 2000，随机）==========
  算法     比较次数 移动次数   轮数
  bubble          1997622      1002731     1947
  selection       1999000         1992     1999
  insertion       1004718      1002731     1999
  shell             33759        22336        7
  quick             24596        14886     1136
  merge             19440        21952     1999
  n*log2(n) ≈ 22000,  n^2 = 4000000
```

**选择排序的独特之处**：比较次数最多（n²/2），但**移动次数最少**（只有 n-1 次交换）。
如果「移动元素」比「比较元素」贵得多（比如元素是几百字节的大结构体），
选择排序反而有优势。

## 4. 输入形态的影响（本节最重要）

```text
========== 4. 输入形态对算法的影响（n = 5000）==========
  算法     输入    比较次数 耗时(ms)
  bubble     随机        12495789     34.661
  selection  随机        12497500     18.612
  insertion  随机         6238073     10.301
  shell      随机          100561      0.513
  quick      随机           70885      0.329
  merge      随机           55251      0.394

  bubble     已排序         4999      0.007     ← O(n)！
  selection  已排序     12497500     16.334     ← 依然 n²/2
  insertion  已排序         4999      0.011     ← O(n)！

  quick      全部相等     12512497     12.410     ← 退化到 O(n²)！
  merge      全部相等        32004      0.134
```

**三个值得注意的地方**：

1. **bubble / insertion 在「已排序」输入下只比较 n-1 次** —— 从 1250 万次降到 4999 次，
   快了近 5000 倍。bubble 靠 `!swapped` 提前退出；insertion 的内层 `while` 一次都不进。
2. **selection 在「已排序」下依然比较 n²/2 次** —— 它从不提前退出。
   这就是为什么它比插入排序慢：**它对输入的有序性完全不敏感**。
3. **quick 在「全部相等」下比较次数接近 n²/2** —— Lomuto 分区遇到全相等时，
   每次只能确定 pivot 这一个元素的位置，递归退化成 n 层。

## 5. 规模增长：验证复杂度

```text
========== 5. 规模增长测试 ==========
  算法           n=2000       n=4000       n=8000
  insertion         1.604        6.313       25.712      ← 倍率 3.9 / 4.1
  shell             0.181        0.388        0.847      ← 倍率 2.1 / 2.2
  quick             0.123        0.244        0.527      ← 倍率 2.0 / 2.2
  merge             0.141        0.251        0.534      ← 倍率 1.8 / 2.1
```

**n 翻倍时**：

- O(n²) 的耗时翻约 **4 倍**（insertion：3.9 / 4.1）
- O(n log n) 的耗时翻约 **2 倍**（quick/merge/shell：2.0~2.2）

看**倍率**比看绝对耗时有意义得多。

## 6. 小规模：谁最快？

```text
========== 6. 小规模对比：n = 32 时谁最快？==========
  算法      总耗时(ms)     单次(ns)
  bubble             20.429         1021.5
  selection          15.009          750.5
  insertion           9.645          482.2
  shell               7.085          354.2
  quick               8.706          435.3
  merge              10.171          508.6
```

**n = 32 时，shell 最快，insertion 第二，merge 反而慢**。

原因：算法有常数因子。递归调用、临时数组分配、函数调用开销，
在小数据量下占比很高。

**这正是标准库的做法**：`std::sort` 递归到小区间时切换成插入排序。

## 最佳实践

1. **默认用标准库的 `qsort`**，不要自己写（除非有特殊需求）。
2. 需要**稳定排序**时：用归并（`qsort` 不保证稳定）。
3. 数据**近乎有序**时：插入排序是 O(n)，别用快排。
4. 数据**可能大量重复**时：用三路快排，否则 Lomuto 会退化成 O(n²)。
5. 元素**很大**（移动昂贵）时：考虑选择排序或指针排序。
6. **测试排序算法必须测四种输入**：随机、已排序、逆序、全部相等。

2. 为什么冒泡排序的「已排序」耗时（0.007 ms）比插入排序（0.011 ms）还低？
