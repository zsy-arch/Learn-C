# 04_b_tree —— B 树：为磁盘而生的多路平衡树

## 本章问题

1. 二叉搜索树每层只能有 2 个分支，如果数据在磁盘上、每次访问一个节点都要一次磁盘 I/O，那"树高"就是"I/O 次数"——B 树用什么办法把树压得更矮？
2. 最小度数 `t` 到底决定了什么？为什么每个节点的 key 数量有"下限"和"上限"，这两个数字是怎么来的？
3. 删除一个 key 的时候，"向兄弟借一个"和"直接合并"是两种完全不同的操作，程序怎么知道该用哪一种？如果要删的 key 恰好在内部节点（不是叶子）上，为什么不能直接删，要先换成前驱或后继？

## 学习目标

- 理解 B 树的核心不变量：每个非 root 节点的 key 数在 `[t-1, 2t-1]` 之间，所有叶子深度相同，且这个不变量是"分裂"和"合并/借"操作存在的唯一原因。
- 亲手实现插入时的节点分裂（split），并看清楚"中间的 key 被推上去"这句话在内存里到底发生了什么。
- 亲手实现删除的全部分支：叶子直接删、叶子下溢后向左/右借、叶子下溢后合并、内部节点删除时替换前驱/后继、根节点收缩。
- 写一个 `btree_verify()`，把"这棵树还是不是一棵合法的 B 树"这件事变成可以在每次操作后自动检查的东西，而不是靠肉眼看 `btree_print()` 的输出猜。
- 亲眼见到一个"分裂中点算错一位"的错误实现是怎么在不触发任何内存错误的情况下,悄悄破坏 B 树的不变量的。
- 同时看清 `btree_verify()` **查不到**什么：它只判断"树现在合法吗"，不判断"这次操作该不该改动它"。本模块修掉的四个缺陷全部落在这个盲区里，其中最典型的一个（重复 key 插入会先分裂再返回 `false`）在上万次随机压力测试里一直在发生，校验器一次都没报警。

## 数据结构定义

本章采用 CLRS（《算法导论》）的"最小度数 `t`"约定，而不是"阶数 `m`"约定（两者只是同一件事的不同参数化方式，`m = 2t`）：

```c
typedef struct BTreeNode {
    int n;                       /* 当前存了几个 key */
    bool is_leaf;
    int *keys;                   /* 容量 2t-1 */
    struct BTreeNode **children; /* 容量 2t，叶子节点不用 */
} BTreeNode;

typedef struct {
    BTreeNode *root; /* 空树时为 NULL */
    int t;            /* 最小度数，t >= 2 */
} BTree;
```

对最小度数为 `t` 的 B 树（`t >= 2`）：

- 每个非 root 节点至少有 `t-1` 个 key，至多 `2t-1` 个 key。
- 每个非 root 内部节点至少有 `t` 个孩子，至多 `2t` 个孩子。
- root 的 key 数上限同样是 `2t-1`，下限则要分两种情况：**叶子 root 可以有 0 个 key**（那就是空树，或者说整棵树只剩 root 这一个节点、且它刚被删空），**内部 root 至少要有 1 个 key**（因为 `n` 个 key 对应 `n+1` 个孩子，`n=0` 意味着它只有 1 个孩子——这种"僵尸 root"应该被它唯一的孩子取代，树高减一）。这个区分不是吹毛求疵：`btree_verify` 最初把 root 的下限一律当成 0，于是"0 个 key + 1 个孩子"的非法树能通过校验，这正是本模块修掉的缺陷之一（见下面"回归测试"一节）。
- 所有叶子的深度相同。
- 节点内的 key 严格递增；对内部节点的第 `i` 个孩子，它子树里的所有 key 都夹在 `keys[i-1]` 和 `keys[i]` 之间（边界情况用 `-∞`/`+∞` 处理）。

**为什么要有"下限"这个东西？** 二叉搜索树的每个节点只装 1 个 key，树高是 `O(log2 n)`。如果把"装多个 key、多个分支"这件事做到极致——每个节点尽量装满、尽量晚分裂——就能用同样的节点数换来更矮的树。但如果不设下限，删除操作可以让节点一直变空而不做任何合并，树会退化回"每个节点 1 个 key"的最坏情况，白白多出很多层。下限保证了"最坏情况下，树高也是 `O(log_t n)`"——这正是 B 树在磁盘等高延迟存储场景下比二叉树快的根本原因：**每一层对应一次昂贵的 I/O，`t` 越大，同样的数据量所需的层数越少。**（本实验用内存里的 `int` key 做教学演示，不涉及真实磁盘 I/O，但节点大小对应磁盘块大小、`t` 对应"一个块能装多少个 key"这套思路是 B 树在数据库、文件系统里的真实用法。）

t=2 时 `2t-1=3`，所以这 7 次插入里有**两次**分裂，而且它们发生在不同的位置：

- **插 40**：满的是 root（`[10 20 30]`）。先造一个新的空 root、把旧 root 挂成它的第 0 个孩子，再分裂——树因此**长高一层**，节点数 1 → 3。

这两种分裂在代码里走的是同一个 `split_child`，区别只在于"谁是被分裂节点的父亲"。之所以要把它们分开讲，是因为第二种很容易在阅读输出时被忽略：它不改树高，如果只盯着 `height` 或只盯着 root 看，就只会注意到插 40 那一次，而插 60 那一次只表现为节点数悄悄 +1。demo 第 1 节因此在每次插入前先算一遍"这次会在哪些位置触发分裂"（`predict_splits`）并打印出来，而不是只检查 `root->n == 2t-1`。分裂特写（对应 demo 第 2 节）：

### 机制剖析：分裂到底在内存里做了什么

`split_child(x, i, t)` 分裂 `x` 的第 `i` 个孩子 `y`（`y` 此时正好装满 `2t-1` 个 key）：

```text
分裂前：              y (2t-1 个 key，装满了)
                      [k0 k1 ... k(t-2) | k(t-1) | k(t) ... k(2t-2)]
                       └── 左半 t-1 个 ──┘  中间   └── 右半 t-1 个 ──┘

分裂后：  x 里插入 k(t-1) 作为新的分隔 key，多出一个孩子指针
          y（原地复用，变成左半） z（新分配，装右半）
          [k0..k(t-2)]            [k(t)..k(2t-2)]
```

具体三步（对应 `btree.c` 的 `split_child`）：

1. **新建节点 `z`**，把 `y` 后半段的 `t-1` 个 key（下标 `t` 到 `2t-2`）复制过去；如果 `y` 不是叶子，还要把对应的 `t` 个孩子指针也复制过去。
2. **`y` 的 `n` 直接改成 `t-1`**——注意这里不需要清空 `y->keys[t..2t-2]`，因为 `n` 已经变小了，那些位置的旧数据永远不会被当作有效 key 读到，下次这个节点再涨到 `n` 个 key 时会被新数据覆盖。这是"逻辑删除"而不是"物理清空"，也是为什么本实验没有在这里做 `memset`。
3. **把中间的 key（下标 `t-1`）搬到父节点 `x` 里**，插入位置是 `i`；同时把新孩子 `z` 的指针插入到 `x->children[i+1]`——插入前要先把 `x` 里下标 `>= i` 的 key 和下标 `>= i+1` 的孩子指针都往后挪一位，腾出空位。

如果被分裂的节点正好是 root，插入前会先检测"root 已经满了吗"，如果满了就先造一个新的空 root、把旧 root 挂成它的第 0 个孩子，再对这个新 root 调用 `split_child(new_root, 0, t)`——这样"root 分裂"和"内部节点分裂"用的是完全同一套代码，不需要为 root 写特殊分支。这也是为什么本实现选择"插入前，如果孩子已满就先分裂"（也叫"下降路径上主动分裂"），而不是"插到叶子后再往上修复"：主动分裂保证递归调用 `insert_nonfull` 时，当前节点一定不满，可以放心往里塞一个 key，完全不用处理"插入之后才发现自己满了，需要往上传递分裂信号"这种回溯逻辑。

## 3. 查找：真实输出

```
========== 3. 查找：命中与未命中 ==========
树结构 (t=3)：
[30 60 90]
  [10 20]
  [40 50]
  [70 80]
  [100 110 120 130]
search(10) = 找到
search(60) = 找到
search(130) = 找到
search(5) = 未找到
search(65) = 未找到
search(999) = 未找到
```

查找的逻辑很直接：在当前节点里从左到右找第一个 `>= key` 的位置 `i`；如果 `keys[i] == key` 就命中；否则如果是叶子就说明整棵树里都没有这个 key，返回未找到；否则递归进入 `children[i]`（因为 B 树的排序性质保证了：如果 key 存在，一定在 `keys[i-1]` 和 `keys[i]` 之间那个子树里）。每下降一层就是一次"磁盘 I/O"（本实验里当然只是一次指针跳转），这正是 `t` 越大、树越矮、查找越快的直接体现。

## 4～8. 删除：先看全貌，再看叶子层的四种情形

删除是本章真正的难点，代码里一共有**7 个**带标号的分支。先把全貌列出来，下面 5～10 节再逐个演示：

| 标号 | 情形 | 在哪一节 |
|---|---|---|
| 1 | key 就在叶子里，且这个叶子删完仍 `>= t-1` —— 直接删 | 第 5 节 |
| 2a | key 在内部节点，左孩子 `n >= t` —— 用**前驱**顶替，递归删前驱 | 第 10 节 |
| 2b | key 在内部节点，左孩子不够、右孩子 `n >= t` —— 用**后继**顶替 | 第 10 节 |
| 2c | key 在内部节点，左右孩子都 `n == t-1` —— 左孩子 + key + 右孩子三者**合并**，再从合并后的节点里删 | 第 10 节 |
| 3a | 下降路径上的孩子 `n == t-1`，左邻居 `n >= t` —— 向左**借**（右旋） | 第 6 节 |
| 3b | 同上，左邻居不够、右邻居 `n >= t` —— 向右**借**（左旋） | 第 7 节 |
| 3c | 同上，两侧邻居都 `n == t-1` —— 和一侧邻居**合并** | 第 8、9 节 |

（注意 2c 和 3c 都是"合并"，但触发条件和作用对象不同：2c 合并的是"要删的 key 两侧的孩子"，3c 合并的是"下降路径上那个太瘦的孩子和它的邻居"。有些教材把它们算作同一种，于是数出"6 种"——本章按代码里实际的分支数算 7 个，因为它们在 `btree.c` 里是两段不同的代码，各自都需要单独的定向测试。同理，标号 1 和 3a/3b/3c 也常被合称为"叶子层的情形"，本节标题里的"四种"就是指这四个。）

### 借（case 3a/3b）的图示

以第 6 节"借左邻居"为例（`t=3`，`fill_child` 里的 3a 分支）：

这里一共有**三个**状态，中间那个很容易被漏掉——它是"借"真正的产物，而 demo 打印出来的只是最后一个：

```text
① 下降之前：     [.. 30 ..]           <- 要删的 40 在右边这个孩子里
                /         \
          [10 15 20 25]   [40 50]
           (n=4, 借得起)   (n=2, 已在下限 t-1=2，不能再少)

② fill_child 借完（还没删 40）：
                 [.. 25 ..]           <- 分隔 key 换成了左邻居的最大 key
                /         \
          [10 15 20]     [30 40 50]   <- 变成 n=3 了，现在删得起 40
           (n=3)           (n=3)

③ 然后才删 40：  [.. 25 ..]
                /         \
          [10 15 20]     [30 50]      <- demo 第 6 节打印的是这一步
           (n=3)           (n=2)
```

**顺序是"先借，后删"，不能反。** 原因就是 ② 这一步的意义：`[40 50]` 只有 2 个 key，正好卡在 `t-1=2` 的下限上，直接删掉 40 会剩 1 个 key，违反不变量。所以 `delete_from` 在下降进这个孩子**之前**先调用 `fill_child` 把它补到 3 个 key，进去之后才是一次普通的"叶子够用，直接删"（也就是第 5 节那种最简单的情形）。反过来做——先删成 `[50]` 再想办法补——就又回到了"下溢向上传播"那套需要回溯的逻辑。

借的搬运过程本身是一次**右旋**：父节点的分隔 key `30` 下沉到右孩子的最前面，左邻居最大的 key `25` 上升去顶替 `30` 的位置。这样做而不是直接把 `25` 塞给右孩子，是因为要维持排序边界——`25` 必须留在"左子树所有 key"和"右子树所有 key"之间，而 `30` 本来就在那个位置上，下沉到右孩子的最前面正好还比右孩子原有的所有 key 都小。整个操作只搬动 3 个 key（一个下沉、一个上升、加上叶子内部的位移），不分配也不释放任何节点——这就是为什么"借"比"合并"便宜，`fill_child` 总是先试借，借不到才合并。

### 合并（case 3c）的图示

以第 8 节为例：

```text
合并之前：   [.. 60 100 ..]
                    /    \
              [80 90]   [110 120]
              (n=2)      (n=2，都在下限，谁也借不出)

合并之后：   [.. 60 ..]
                  \
            [80 90 100 120]
                 (n=4)
```

分隔 key `100` 被拉下来塞进合并后节点的中间，父节点从 3 个 key 减少到 2 个，两个孩子变成一个。

**那么父节点如果因此跌到下限以下呢？在本实现里，这件事永远不会发生。** 这是容易想错的一点，值得说清楚：教科书式的描述常常是"下溢向上递归传递，直到某一层不再下溢或者传到 root"，但那是"**自底向上**"（先删，再回头修）的写法。本实现是**自顶向下**的——`delete_from` 在**下降之前**就调用 `fill_child`，把即将进入的那个孩子先补到 `n >= t`，然后才递归进去：

```text
自底向上（不是本实现）：一路下降到叶子 -> 删 -> 发现下溢 -> 借/合并
                        -> 父节点可能因此下溢 -> 继续往上修 -> ... -> root
自顶向下（本实现）：     每下降一层之前，先把下一层那个孩子补到 n >= t
                        -> 因为任何一层被"抽走"一个 key 之前都已经有 t 个
                        -> 抽走后仍有 t-1 个，不可能下溢 -> 不需要回头
```

也就是说，合并使父节点 key 数减一这件事确实发生了，但 `fill_child` 只会在父节点 `n >= t` 时被调用，减一之后至少还有 `t-1` 个，**恰好不越界**。整个删除过程中唯一一处"向上"的动作是 `btree_delete` 在 `delete_from` 返回之后做的那一次 root 检查（`root->n == 0` 就让唯一的孩子顶上，树高减一，见下面第 9 节）——它只做一次，不是循环也不是递归，因为只有 root 不受 `t-1` 下限的约束，也只有 root 可能被抽空。

这和插入侧的**主动分裂**是同一个设计思想的两半：插入时"下降前先把满的孩子分裂掉"，所以插入不需要向上传播分裂信号；删除时"下降前先把瘦的孩子补胖"，所以删除不需要向上传播下溢信号。两边都是用"提前一步做掉"换"不需要回溯"。

## 9. Root 收缩：合并恰好把 root 抽空

上面第 8 节的合并发生在 root 的孩子这一层，合并让 root 从 3 个 key 掉到 2 个，还够用。如果 root 本来就只有 1 个 key，合并把它也抽走了呢？那 root 就剩 0 个 key、挂着唯一一个孩子——这是唯一一种需要"向上"处理的情形，也是 `btree_delete` 里那一次（仅一次、非递归）root 检查存在的理由。专门构造一棵更小的树来只演示它：

```
========== 9. 专门构造一棵树，强制走一次纯粹的合并 (case 3c) ==========
t=2, 插入 10,20,30,40 之后：
[20]
  [10]
  [30 40]
root=[20]，孩子 [10] 和 [30 40]。

删 40 之后（右孩子降到 [30]，n=1=下限）：
[20]
  [10]
  [30]
  [verify ok after delete 40]

现在删 10：左孩子 [10] 本身就是要删的那个 key 所在的叶子，
删完它会变空（n=0）。它唯一的邻居 [30] 也在下限（n=1），没法借，
=> 必须合并：把分隔 key 20 和右孩子 [30] 一起并入左孩子，
合并后 root 变空，树整体降一层。
[20 30]
height=0（从 1 降到 0，root 从内部节点变成了唯一的叶子）
  [verify ok after delete 10 (pure merge, root shrinks)]
```

关键的一步藏在"删 10"里：删除的目标 key 恰好就在要被合并掉的那个叶子里，所以合并和删除是同一次操作完成的——`merge_children` 把 `[10]`、分隔 key `20`、`[30]` 拼成 `[10 20 30]`，然后再从这个新节点里把 10 删掉，剩下 `[20 30]`。`btree_delete` 在 `delete_from` 返回之后检查一次 `root->n == 0`：如果是，就把这个空 root 释放掉，让它唯一的孩子（这里就是刚合并出来的 `[20 30]`）取代它成为新 root，树高随之减少 1。注意这一步在代码里就是一行三元表达式：

```c
    if (tree->root->n == 0) {
        BTreeNode *old_root = tree->root;
        tree->root = old_root->is_leaf ? NULL : old_root->children[0];
        node_free(old_root);
    }
```

`is_leaf` 这个分支把两种"root 被抽空"分了开：root 是**内部节点**时（就是本节这种情形），它必定只剩 `children[0]` 这一个孩子，让孩子顶上、树高减一；root 是**叶子**时，它没有孩子可以顶上，说明刚删掉的是整棵树最后一个 key，于是新 root 是 `NULL`，对应 `btree_height` 返回 `-1` 的空树状态。`tests.c` 的 `test_root_shrinks_after_merge` 把两个分支连着走了一遍：先删到 `height` 从 1 变 0（内部 root 让孩子顶上），再删掉最后那个 key 断言 `t.root == NULL`（叶子 root 直接清空）。demo 第 11 节（一直删到空树）则是插入 1..15 再顺序删光，每一步都过一次 `btree_verify`。这是唯一一处"树的高度会减少"的地方——其余所有借/合并操作都发生在 root 以下，不影响树高。

## 10. 删除内部节点的 key：case 2a / 2b / 2c

前面 5～9 节删的都是叶子里的 key。如果要删的 key 就在**内部节点**上（不是叶子），不能直接从数组里抠掉它——内部节点的 key 同时充当"左右子树的分隔线"，直接删会破坏"左子树全部小于它、右子树全部大于它"这条排序性质，`x->children[i]` 和 `x->children[i+1]` 之间就失去了那条分隔线。正确做法是**先找一个能顶替它、又不破坏排序性质的 key，把这个 key"提"上来，然后把原来的问题转化成"从子树里删掉那个被提上来的 key"**——这样递归下去，最终一定会落到某个叶子上，变成前面已经解决的简单情形。

能顶替的 key 只有两种候选：**前驱**（左子树里最大的 key，一定小于 `keys[i]` 但大于左子树里所有别的 key）和**后继**（右子树里最小的 key，性质对称）。选哪一个，看哪边"借得起"：

```
========== 10. 删除一个存在于内部节点的 key：前驱/后继替换 ==========
case 2a（偷前驱）：插入 20,10,30,5,15 之后：
[20]
  [5 10 15]
  [30]
root=[20]，左孩子 [5 10 15]（n=3，够借），右孩子 [30]（n=1，下限）。
删 20：它是内部节点的 key。检查左孩子，n=3>=t=2，够借
=> 用左子树里最大的 key（前驱，也就是 15）顶替 20，
然后递归地把 15 从左子树里删掉。
[15]
  [5 10]
  [30]
root 现在的 key 是 15（前驱 15 被提上来了）
  [verify ok after delete 20 (internal, case 2a predecessor)]

case 2b（偷后继）：插入 20,10,30,40,35 之后：
[20]
  [10]
  [30 35 40]
root=[20]，左孩子 [10]（n=1，下限，不够借），右孩子 [30 35 40]（n=3，够借）。
删 20：左孩子不够借，看右孩子，n=3>=t=2，够借
=> 用右子树里最小的 key（后继，也就是 30）顶替 20，
然后递归地把 30 从右子树里删掉。
[30]
  [10]
  [35 40]
root 现在的 key 是 30（后继 30 被提上来了）
  [verify ok after delete 20 (internal, case 2b successor)]
```

判断规则（对应 `btree.c` 的 `delete_from` 里处理"找到了要删的 key 但当前节点不是叶子"的分支）：

- **case 2a**：左孩子 `n >= t`（够借）—— 用前驱顶替，递归删前驱。
- **case 2b**：左孩子不够借，但右孩子 `n >= t` —— 用后继顶替，递归删后继。
- **case 2c**：左右孩子都恰好 `n == t-1`（都不够借）—— 干脆把左孩子、要删的 key、右孩子三者合并成一个节点，这个 key 现在"埋"在合并后的节点里，对合并后的节点递归调用 `delete_from` 把它删掉（这时它已经变成了"从一个节点里删 key"的情形，可能继续往下传递）。`tests.c` 的 `test_delete_internal_case2c_merge` 专门构造了两个孩子都恰好 `n == t-1` 的场景来触发这一分支，合并之后树高从 1 降到 0。

无论走哪条分支，"提上来的 key"最终都会被**递归删除**而不是直接从数组里抹掉——这保证了如果递归过程中子树本身也下溢了，借/合并的逻辑照样会被正确触发，不会因为走了"内部节点删除"这条特殊路径就绕过下溢检查。三种情形的共同点：**内部节点的 key 永远不会被"抹除"，只会被替换、搬运，或者和别的 key 一起合并到别处**——它始终留在树里的某个位置，直到真正递归删到某个叶子层，才会发生数组意义上的物理移除。

## 12. 错误示例：分裂中点算错一位，会怎样

前面所有正确演示都反复用到一个数字：分裂满节点时，中间下标是 `t-1`。如果这个 `-1` 被漏掉会怎样？下面这段不是让真正的 `BTree` 跑出错误结果（那样反而会掩盖问题——一棵已经不合法的树后续行为不可预测，没有教学意义），而是在 `demo.c` 里用一个独立的、只有 `n`/`keys[8]` 两个字段的最小结构体单独摆出这个算术错误，纯粹展示"错在哪、错的后果是什么"：

```
========== 12. 错误示例：分裂中点算错一位，会怎样 ==========
满叶子 [1 2 3 4 5]（t=3，最多 2t-1=5 个 key）要分裂。
正确做法：中间下标是 t-1=2，也就是 key[2]=3 被推上去，
左边留 t-1=2 个，右边留 t-1=2 个。

错误版本：把中间下标写成了 t=3（漏了 -1），key[3]=4 被推上去，
左边留 3 个，右边留 1 个。
最少要求每个非 root 节点有 t-1=2 个 key，右边只有 1 个 -> 违反不变量！
这种 bug 不会让程序崩溃，也不会被 sanitizer 抓到（没有非法内存访问），
查找、插入在小规模测试下可能看起来都“正常工作”，直到某次删除因为
某个节点的 key 数比假设的下限还少，触发数组下标或逻辑上的错误。
唯一可靠的防线就是 btree_verify()：每次插入/删除后跑一次，
任何不变量被破坏都会在“案发现场”被抓到，而不是等到很久以后才崩溃。
```

这个例子想说明的是一类**逻辑腐化型 bug**——错误的下标算出来的 `left_n=3`、`right_n=1` 都是合法的数组访问，不会踩到越界，`-fsanitize=address,undefined` 在这里完全无能为力，因为从内存安全的角度看这段代码没有任何问题，它只是"算错了应该算的数"。这种 bug 只能靠**语义层面的不变量检查**（也就是 `btree_verify()` 检查 `n >= t-1`）抓到，而且必须在**每一次**分裂之后立刻检查，因为如果只在最后统一检查一次，出问题时已经经过了很多次后续的插入/删除，`btree_print()` 打出来的树早就面目全非，很难倒推出"到底是哪一次分裂时中点算错了"。这也是为什么本章从 `demo.c` 第 1 节开始，每一次插入/删除之后都紧跟一次 `verify_or_die()`（`demo.c:15` 定义，对 `btree_verify` 的薄包装，失败时打印错误信息并 `exit(1)`），而不是等演示全部跑完再检查一次。

## 属性校验：`btree_verify()` 具体检查什么

光靠 `btree_search()` 找得到、`btree_count_keys()` 数得对，并不能证明这棵树的**结构**是合法的——一棵严重违反不变量的树完全可能因为"凑巧"而查找结果正确（比如 key 排序没乱，只是某个节点 key 数超了范围）。`btree_verify(tree, err_buf, err_buf_size)`（`btree.c` 末尾，实际检查逻辑在它上面的 `verify_rec`）对整棵树做一次递归遍历，逐一检查五条不变量，任何一条不满足就立刻停止并把具体原因写进 `err_buf`：

1. **key 数范围**：上限一律是 `x->n <= 2t-1`；下限分三档——非 root 节点是 `t-1`，**叶子** root 是 `0`（空树合法），**内部** root 是 `1`。代码就是这三行：

   ```c
   if (x->is_leaf) min_keys = is_root ? 0 : t - 1;
   else            min_keys = is_root ? 1 : t - 1;
   if (x->n < min_keys) { fail(ctx, "node has %d keys, min is %d (is_root=%d)", ...); return; }
   ```

   把内部 root 那档也写成 `0` 就是本模块修掉的缺陷之一：`n=0` 的内部 root 只有 1 个孩子，是一棵本该收缩掉的树，但校验器会放它过去。
2. **节点内严格递增**：`x->keys[i] < x->keys[i+1]` 对所有 `i` 成立——如果插入逻辑有 bug 导致 key 被插到了错误的位置，这里会立刻抓到。
3. **跨节点的排序边界**：递归下降时把"这个子树允许的 key 范围"作为 `min_key`/`max_key` 一路往下传（第 `i` 个孩子的合法范围是 `(keys[i-1], keys[i])`，边界用 `NULL` 表示 `-∞`/`+∞`），子树里所有 key 必须落在这个区间内——这一条专门抓"分裂/合并/借的时候把某个 key 或子树接错了位置"这类问题，只检查单个节点内部递增是抓不到的。
4. **叶子深度一致**：用一个共享的 `leaf_depth_out` 指针记录第一次遇到的叶子深度，后续每个叶子都必须等于这个深度——一旦不等，说明某次借/合并/根收缩把树"削"得不平衡了。
5. **内部节点孩子指针非空**：`x->n+1` 个孩子指针一个都不能是 `NULL`。

`tests.c` 里几乎每一次 `btree_insert`/`btree_delete` 之后都紧跟一次 `verify_ok()`（对 `btree_verify` 的薄包装，失败时打印错误信息），而不是只在测试函数末尾验证一次——原因和上面第 12 节的教训一致：只有每一步都验证，才能保证"发现问题的那一刻"就是"问题实际发生的那一刻"，而不是隔了几十次操作之后才发现树已经不对了，却无法定位是哪一步出的错。26 个测试里覆盖的构造场景包括 t=2/3/4 度数、60~2000 个 key 的顺序/随机插入、7 个删除分支各自的定向构造、以及 4 组不同 `t`（2/3/5/10）、不同规模（1000~2000 key）、固定种子的随机压力测试（自定义 `xorshift32`，而非 libc 的 `rand()`，保证跨平台可复现）。

但要留意 `btree_verify()` 能力的边界，它只回答一个问题：**"这棵树现在还是一棵合法的 B 树吗"**。它不回答"这棵树是不是我预期的那棵树"，更不回答"刚才那次操作该不该改动它"。下面"回归测试"一节的四个缺陷全部落在这个盲区里——每一个都能让 `btree_verify()` 一路绿灯。

## 调试笔记：三次因为"没先验证树的真实形状"而写错的测试

实现 `btree.c` 本身的过程中，`insert`/`split_child`/`delete_from`/`fill_child`/`merge_children` 没有出现过真正的算法 bug——随机压力测试配合每一步 `btree_verify()` 一直是干净的（`tests.c` 里四组随机压力测试加上其余用例，实测一共 6469 次 `btree_insert` + 6212 次 `btree_delete` = 12,681 次修改操作，以及 12,420 次 `btree_verify`；这个数字是用一份把 `btree_insert`/`btree_delete`/`btree_verify` 重命名后套上计数壳子的构建量出来的，不是估的）。但在**编写针对具体分支的定向测试**时，连续踩了三次同一类坑，记录下来是因为这类错误本身很有教学价值：

1. **假设错了一棵树的形状**。写 `test_delete_leaf_case3a_borrow_left` 时，凭直觉认为对 `t=2` 的树依次插入 `10,20,30,40,50,60,70` 会得到 `root=[40]`、两个各装 3 个 key 的孩子 `[10,20,30]`/`[50,60,70]`。断言按这个假设写完，一跑就 `FAILED CHECK: t.root->n == 1 && t.root->keys[0] == 40`。真正打印出来的树是 `root=[20,40]`，三个孩子分别是 `[10]`、`[30]`、`[50,60,70]`。

   为什么会差这么多：`t=2` 时容量只有 3 个 key，这个序列其实触发了**两次**分裂（插 40 时分裂 root，插 60 时分裂孩子 `[30 40 50]`，见上面第 1 节），而我脑子里只算了一次，于是把两次分裂的结果误当成一次的结果。插 70 那一步倒确实没有分裂——`[50 60]` 只有 2 个 key，还没满，70 直接塞进去变成 `[50 60 70]`。这不是算法错了：在此之前，跑了上万次操作、每步都验证的随机压力测试已经证明了核心逻辑没问题。真正的问题是我在写断言之前没有先拿 `btree_print()` 把真实结构打出来看一眼，而是凑了一个"感觉上应该长这样"的形状。修复方式是构造一棵更小、更容易手工验证的树（`{10,20,30,40}`，删 40，插入 5，再删 30），并且**先用一个独立的小程序把每一步的真实结构打印出来确认无误，再去写断言**。
2. **同一类问题在写 case 3b 测试时又犯了一次**，只是这次在写断言之前多了一点警觉——注意到自己并不能确定构造出的场景是否真的触发了"向右借"而不是别的分支，于是主动先用 `btree_print()` 把真实的中间状态打出来，确认了删除 10 之后确实是把根的分隔 key 压进左孩子、右邻居的最小 key 提上来，才把这个过程写进测试文件的注释里（现在 `tests.c` 里那段注释描述的每一步都是照着真实输出写的，不是推测）。顺带一提，上面第 6 节那张"借"的三态图之所以要画出中间状态 `[30 40 50]`，也是同一个教训的产物：只看 demo 的最终输出 `[30 50]`，很容易把"借完的样子"和"借完又删完的样子"混成一个。
3. **验证了树的形状，但对"前驱被偷走之后还在不在树里"这件事想错了**。`test_delete_internal_case2a_steal_predecessor` 一开始写的是 `CHECK(!btree_search(&t, 15))`，隐含的假设是"被当作前驱抢走的 key 15，删除之后就不存在了"。这是对 B 树 case 2a 语义的误解：前驱 key 只是**从叶子搬到了内部节点**，顶替了被删的那个 key 的位置，它本身依然是树里一个合法、可查找的 key，只是换了个"住址"。跑测试时看到 `[FAIL] test_delete_internal_case2a_steal_predecessor`，才意识到断言反了，改成 `CHECK(btree_search(&t, 15))`（并在旁边写清楚"15 依然存在——现在住在 root 里，不在叶子里了"）。

三次错误的共同教训：**"先用 `btree_print()` 把真实结构打出来看一眼再写断言"** 比"凭对算法的理解直接写断言，跑了再改"更省时间，尤其是在 B 树这种"同一个插入序列，不同的 `t` 会产生完全不同形状"的结构上，直觉常常是错的。这也是为什么整个 `btree.c` 的核心实现反而没有犯过这类错误——它的正确性完全交给了"上万次随机操作 + 每步验证"的压力测试去检验，而不是依赖对着某个具体形状的手工推断。

但这条教训也有它的**盲区**，而且本模块正好撞上了：压力测试只能发现"树变得不合法"，发现不了"树变了但不该变"。下一节那个重复 key 缺陷就是这样溜过去的——上万次随机操作里它一直在发生，`btree_verify()` 一次都没报警，因为每次分裂出来的树都是完全合法的 B 树。

## 回归测试：守住四个 `btree_verify` 查不出来的缺陷

上面那 6 个新增用例（`test_dup_insert_*` 四个、`test_verify_root_min_keys_*`、`test_delete_never_leaves_keyless_internal_root`）加上独立的 `guard_check`，针对的是本模块修掉的四个缺陷。它们有一个共同点，也正是值得单独写回归测试的原因：**`btree_verify()` 一个都抓不到**。

| 缺陷 | 为什么校验器抓不到 | 谁来守 |
|---|---|---|
| `btree_insert` 撞上重复 key 时，若 **root** 恰好满，会先做一次预分裂再返回 `false` | 分裂后的树仍然是一棵**合法**的 B 树，只是凭空高了一层。契约写的是"返回 false 时不做任何修改"，而校验器只检查合法性，不检查"有没有改" | `test_dup_insert_into_full_leaf_root_is_noop`、`..._full_internal_root_is_noop`、`..._full_root_t3` |
| 同一个缺陷的**另一半**：撞上重复 key 时，若**下降路径上任意一层的孩子**恰好满，`insert_nonfull` 也会先 `split_child` 再比较 | 同上——树依然合法。而且这一半比上一半更隐蔽：三个已有的回归用例构造的树 root 全是满的，每次都被第一道检查挡住了，这条路径根本没被走到 | `test_dup_insert_into_full_child_is_noop` |
| `btree_verify` 自己把 root 的 key 数下限一律当成 0，于是"root 有 0 个 key、挂着 1 个孩子"的树能通过校验 | 这是校验器本身的 bug——它就是那个本该报警的人 | `test_verify_root_min_keys_splits_leaf_and_internal` |
| `btree_create(1)` 不拦：`2t-1 = 1`，整棵树退化成链；`t <= 0` 时 `2*t-1` 转成 `size_t` 变成接近 `SIZE_MAX` 的巨值 | 每一步操作都"合法"，只是这个结构从一开始就不是 B 树 | `guard_check`（`make guard`） |

### 重复 key 缺陷值得单独讲：一个"修了一半"的修复

这个缺陷的根源是**主动分裂和"不修改"契约在时序上天然冲突**：主动分裂的规则是"进入一个孩子之前，如果它满了就先分裂它"，而"这个 key 是不是重复的"这个判断，只有在**分裂之后**、拿被提上去的那个 key 做比较时才能得出。所以任何"边下降边判重"的写法，都会在某条路径上先改结构、后发现重复。一共两条路径：

```text
路径 (1) root 满：       btree_insert 无条件新建 root + 分裂旧 root
                         -> 然后才交给 insert_nonfull 去发现重复
                         -> 节点数 1 -> 3，树高 0 -> 1

路径 (2) 下降途中某个孩子满：insert_nonfull 先 split_child
                         -> 分裂之后才 `if (key == x->keys[i]) return false;`
                         -> 节点数 +1，树高不变
```

**第一版修复只堵住了 (1)**，在 `if (tree->root->n == 2*t-1)` 里面加了一次 `btree_search`。它之所以看起来是对的，是因为当时三个回归用例（`..._full_leaf_root`、`..._full_internal_root`、`..._full_root_t3`）构造的树 **root 全是满的**，每次都在 (1) 处就被挡住返回了，`insert_nonfull` 里那条路径根本没机会执行。测试全绿，缺陷还在。

暴露 (2) 只需要一棵 **root 不满、但某个孩子满**的树。t=2，插入 `10,20,30,40,50`：

```text
插入已存在的 40 之前：  [20]              节点数 3
                       /   \
                    [10]   [30 40 50]    <- root 只有 1 个 key（不满），
                                            但这个孩子 n=3=2t-1（满了）

插入已存在的 40 之后：  [20 40]           节点数 4  <- 树被改了！
                       /  |  \              然后才返回 false
                    [10] [30] [50]
```

返回值是对的（`false`），树也**仍然是一棵完全合法的 B 树**——所以 `btree_verify()` 一个字都不会说。调用方看到 `false` 会认为"什么都没发生"，而实际上节点数已经变了。插 `30` 或 `50` 同样会先触发这次分裂，只是重复是在更深一层才被发现。

最终的修复是把检查提到 `btree_insert` 最前面（`if (btree_search(tree, key)) return false;`），在任何结构改动之前就返回，两条路径一起覆盖。代价是每次插入多一次 `O(log_t n)` 下降，实测慢 1.5~1.7 倍（见下面性能一节的 A/B 数据）；选择付这个代价而不是保留一条静默违约的路径，理由是前者可测量、后者不可见。`test_dup_insert_into_full_child_is_noop` 专门钉住 (2)：它构造上面那棵 t=2 的树，把 `30`/`40`/`50`（左半 / 被提上去的中间键 / 右半）各撞一遍，再用 t=3 的 `[3|[1 2][4 5 6 7 8]]` 把 `4..8` 全撞一遍。

**这一段的教训比缺陷本身更值得记住**：回归测试全绿不等于缺陷修完了，还要问一句"我的用例覆盖到了这个缺陷的全部触发路径吗"。这里三个用例恰好都只走了其中一条，而它们通过的原因（root 满）正是屏蔽另一条路径的原因——用例的构造方式和缺陷的藏身处是相关的，这种相关性会让一整组测试同时失明。

### 四个断言手法，对应四种查不到的东西

1. **结构指纹，而不是聚合计数。** 判断"树有没有被改动"不能只比 `height`/`count_nodes`/`count_keys`——这些是聚合量，可以一起说谎（一次分裂加一次合并就能把节点数还原）。`shape_of()` 把整棵树序列化成 `"[k k|<child><child>]"`，记录**哪一层的哪个节点装着哪些 key**，插入前后逐字节比较。前三个用例分别构造 t=2 的满叶子 root、t=2 的满内部 root（height=1，5 个节点）、t=3 的满内部 root（n=5=2t-1，7 个节点），并且把树里**每一个**已有 key 都拿去撞一遍。
2. **让构造刻意避开"上一道检查"。** `test_dup_insert_into_full_child_is_noop` 的断言手法和上面三个完全一样（还是比结构指纹），区别全在**构造**上：它显式断言 `t.root->n < 2*t-1`（root 不满）**并且** `t.root->children[1]->n == 2*t-1`（孩子满了），把"必须绕过第一道检查才能测到第二条路径"这个前提写成了可执行的断言。这两行断言本身就是这个用例的文档——如果将来有人改动构造导致 root 又变满了，用例会立刻在这两行失败，而不是悄悄退化成第 1 组的重复。
3. **直接测校验器的判定本身。** `test_verify_root_min_keys_splits_leaf_and_internal` 手工拼出三棵树：非叶 root 带 0 个 key + 1 个孩子（**必须判失败**，且错误信息里要出现 `"min is 1"`）、叶子 root 带 0 个 key（**必须判通过**，那就是空树）、非叶 root 带 1 个 key + 2 个最小合法孩子（**必须判通过**）。两个"必须通过"的对照组是关键——它们钉死了失败的原因是 `n == 0`，而不是"内部节点"这件事本身。所以这个用例是双向的：`min_keys` 放太松（内部 root 接受 0 个 key）和收太紧（叶子 root 拒绝空树）都会让它失败。手工拼节点靠 `make_node()`，它照抄 `btree.c` 里 `node_create` 的分配布局（keys 容量 `2t-1`，children 容量 `2t`），这样 `btree_destroy` 能把它干净地释放掉，ASan 下不留痕。
4. **跑真实的删除路径，断言校验器之外的不变量。** `test_delete_never_leaves_keyless_internal_root` 对 t=2/3/4、n=60 的树从两端往中间删，每删一次除了 `verify_ok()` 还额外断言 `t.root->is_leaf || t.root->n >= 1`。这一条不是多余的：它在 `min_keys` 被改坏时**不会**失败（那是校验器的 bug，不是删除的 bug），但当 `btree_delete` 的根收缩逻辑被破坏、同时校验器又被蒙住眼睛时，靠的就是这个直接断言。

每个用例都用"在一份拷贝里单独回退对应的修复，然后跑全套"验证过有没有牙齿。四组回退各自的真实结果：

| 回退什么 | 结果 | 失败的用例 |
|---|---|---|
| 完全去掉重复 key 预检查 | 22/26 | `test_dup_insert_into_full_leaf_root_is_noop`、`..._full_internal_root_is_noop`、`..._full_child_is_noop`、`..._full_root_t3` |
| 只恢复**第一版**修复（守卫挪回 root 满那条分支里） | 25/26 | **只有** `test_dup_insert_into_full_child_is_noop` |
| `verify_rec` 的 `min_keys` 把内部 root 下限改回 `0` | 25/26 | **只有** `test_verify_root_min_keys_splits_leaf_and_internal` |
| 删掉 `btree_create` 的 `t < 2` 守卫 | 测试仍 26/26 | `make guard` 失败（这也是它为什么必须是独立进程） |

第二行是这组回归测试里最关键的一次验证：它证明新增的那个用例**精确地**指向第一版修复漏掉的那条路径——不是"多一个用例多一层保险"，而是"少了它，一个真实存在的缺陷会继续全绿通过"。四组回退之间没有任何串扰，每一组失败的用例集合都恰好是预期的那一个。

### 为什么 `guard_check` 不在 `tests.c` 里

`t < 2` 的守卫是"打一行 stderr 然后 `exit(1)`"，同进程里测不了，只能 `fork()` 子进程看退出码。但 macOS 的 `leaks --atExit` 撞上 `fork()` 会**永久挂死**（实测 90 秒仍未返回，`_exit` 和 `exit` 两种写法都一样），而本平台 LeakSanitizer 又不可用——`leaks` 是唯一能用的泄漏检测手段。一个 `fork()` 就能让整个 suite 变成泄漏检测的死角，代价远大于收益，所以这个用例搬成了独立的可执行文件。

`guard_check` 的退出码语义是**刻意反着写**的：`exit(0)` 表示 `btree_create` 放行了非法的 `t`（守卫失效），守卫自己的 `exit(1)` 才是预期结果，所以 Makefile 里的断言是"这条命令必须失败"。而且只认 `exit(1)` **加上**那行特定诊断（`t must be >= 2`）——因为 `node_create` 里 malloc 失败也是 `exit(1)`，光看退出码的话，守卫被删掉之后 `t <= 0` 引发的巨量 malloc 失败会冒充成"守卫生效"。

## 设计问题：为什么在下降路径上"主动分裂"，而不是插完再修复

`insert_nonfull` 递归下降时，一旦发现"即将要进入的那个孩子已经满了"，会立刻先对它调用 `split_child`，再继续递归——这被称为**主动分裂**（proactive/eager splitting）。另一种同样正确的实现思路是**先插到叶子，再往上检查是否超限、需要分裂**（类似红黑树插入后再旋转修复的风格）。两种思路都能实现正确的 B 树，本章选择前者，原因是：

- 主动分裂保证了递归调用 `insert_nonfull(x->children[i], key, t)` 时，`x->children[i]` **一定不满**（`n <= 2t-2`），可以放心往里插入一个新 key 而不会超过 `2t-1` 的上限——不需要专门判断"插入后是否超限"。
- 分裂动作永远只发生在"当前节点"和"它的直接孩子"之间，不需要额外的回溯/信号传递机制来通知上一层"你的孩子刚刚分裂了，你可能也需要处理"。
- root 分裂可以被表述为"给 root 找一个新的父节点，再对这个新父节点的第 0 个孩子（也就是旧 root）调用 `split_child`"——完全复用内部节点分裂的同一份代码，不需要为 root 写特殊分支（对比 `btree_insert` 里对 `tree->root->n == 2*t-1` 的检查和红黑树里"根节点重新着色"这类特判逻辑）。

代价有两个，第二个是本模块真正踩到的：

1. **可能做了不必要的分裂**：即使某个孩子分裂之后其实并不需要（比如目标 key 最终插的位置离它很远），也已经执行了一次分裂。但由于分裂只是"一次性地把一个满节点拆成两个半满节点"，均摊下来不会影响插入操作 `O(log_t n)` 的复杂度。这个代价是教科书上会提的。
2. **和"重复 key 不修改任何东西"这条契约在时序上冲突**：分裂发生在比较**之前**，所以"边下降边判重"必然存在"已经改了结构才发现是重复"的路径。这个代价教科书一般不提，因为 CLRS 的 `B-TREE-INSERT` 压根不承诺处理重复 key。本实现的 `btree.h` 承诺了，于是只能在 `btree_insert` 最前面加一次完整的预查找——用一次额外下降换契约无条件成立。详见上面"回归测试"一节。

值得注意的是这两个代价方向相反：主动分裂省掉的是"回溯机制"，付出的是"偶尔多分裂一次 + 判重必须前置"。如果改成自底向上的实现，判重可以自然地在到达叶子时完成、一个字节都不用多改，但要换来一整套向上传递分裂信号的逻辑。没有免费的那一版。

## 性能测试：真实测量数据

`tests.c` 里的随机压力测试关心"结构对不对"，不关心"跑得快不快"。这里单独写了一个 `perf.c`，用 `-O2` 编译（`demo.c`/`tests.c` 为了保留调试信息、方便配合 sanitizer 排错，一直用的是 `-O0 -g`；性能测量要看真实优化后的耗时，所以单独换成 `-O2`），在同一台机器上实际测量三个不同最小度数 `t`（2、8、64）、三种规模（1000、1 万、10 万个 key，随机顺序，`xorshift32` 固定种子保证可复现）下的插入、查找、删除耗时，以及"range query 需要访问多少个节点"——后者是为了给 B+-tree 章节的叶子链表扫描做真实的对比基准（B 树没有叶子链表，做区间查询只能靠中序遍历在内部节点和叶子之间反复上下）。

编译与运行：

```bash
cc -std=c17 -Wall -Wextra -Wpedantic -Werror -O2 -g btree.c perf.c -o perf && ./perf
```

摘录真实输出（完整输出见 `perf_out.txt`，跑在本机、当次运行、未编造）：


（`perf.c` 里的 range query 宽度列表是 `{10, 100, 1000, n/10}`，在 `n=1000` 时 `n/10` 正好等于 100，会和前一档撞上；而 `n=1000` 时宽度 1000 又会被 `high >= n` 截断成 499。所以 `perf.c` 现在按**截断后的真实宽度**去重，同一个宽度只测一次——早先的 `perf_out.txt` 里 `t=2, n=1000` 那一组打印了两行一模一样的 `width 100`，就是这个原因。）

每次 bulk insert/delete 之后 `perf.c` 都会调用 `btree_verify()`，三组 `t` 全部通过（`perf_out.txt` 里没有任何 `VERIFY FAILED` 输出），说明这些树高、节点数不是靠肉眼估的，是在真正合法的 B 树上量出来的。三个观察：

1. **`t` 越大，树越矮，范围查询访问的节点越少**：同样 10 万个 key、同样宽度 10000 的 range query，`t=2` 要访问 5706 个节点，`t=8` 降到 983，`t=64` 只需要 121——因为更大的 `t` 让每个节点装更多 key，`log_t n` 直接变小。这就是"I/O 一次装一个磁盘块，块越大越好"这个直觉在真实测量里的样子。
2. **查找的单次操作耗时随 `t` 增大而更快**（`t=2` 约 0.126 us/op，`t=8` 约 0.056，`t=64` 约 0.046）：虽然大 `t` 意味着单个节点内部要做更长的线性扫描，但树高降低带来的收益更大，两者相抵仍是净赚。插入这一列在本实现里看不出同样清晰的趋势（0.194 / 0.098 / 0.097），原因见下面的 A/B 数据——插入被"重复 key 预检查"这一次额外下降摊了一层，而这次额外下降的开销恰好随 `t` 增大而变重，正好抵消了一部分树高的收益。
3. **range query 访问的节点数远大于命中的 key 数**（`t=2` 时访问 5706 个节点只为了命中 10001 个 key）：因为大部分被访问的内部节点本身不含目标区间内的 key，只是"路过"去定位叶子——这正是 B+-tree 章节要解决的问题：如果所有实际数据都在叶子、叶子之间又有链表相连，区间查询就只需要定位一次起点、然后线性扫叶子链表，不需要反复经过内部节点。

### A/B 测量：重复 key 预检查到底花了多少

"在 `btree_insert` 最前面加一次完整查找"这个修复的开销值得单独量一下，因为它是本模块唯一一处**为了契约正确性而主动付出的性能代价**。做法是把 `btree.c` 拷一份、只删掉那一行预检查，然后两个二进制**交替**各跑 3 轮（交替是为了让热降频、调度抖动这类漂移平等地落在两边），丢掉第一轮冷 cache 的离群点，取后两轮。10 万个随机 key 的插入：

| `t` | 树高 | 没有预检查 | 有预检查 | 倍数 |
|---|---|---|---|---|
| 2 | 12 | 0.137 us/op | 0.210 us/op | ×1.53 |
| 8 | 4 | 0.060 us/op | 0.099 us/op | ×1.64 |
| 64 | 2 | 0.056 us/op | 0.097 us/op | ×1.73 |

（"有预检查"这一列和上面 `perf_out.txt` 摘录里的插入数字不完全相等——比如 `t=2` 这里是 0.210、那里是 0.194——因为它们是两次独立的运行。这个量级的浮动就是同一台机器上同一份二进制的正常抖动，也正是为什么倍数要靠**交替跑、取多轮**得出，而不是拿两次孤立的运行相除。）

**注意倍数的方向和直觉相反**：树最高的 `t=2` 涨得最少，树最矮的 `t=64` 涨得最多。这一点很容易想错（我第一次写这段注释就写反了，以为"12 层的树多走一整趟当然最贵"）。真实原因有两层：

- 预检查走的正是紧接着那次插入要走的**同一条路径**，节点都还在 cache 里，所以省掉的是访存开销，**省不掉的是节点内那趟线性比较**——而线性比较的长度正比于 `t`（`t=64` 的节点最多装 127 个 key，每层都要扫）。
- `t=2` 那边插入的耗时大头根本不是下降，而是分裂时的 `memmove` 和 `malloc`（10 万个 key 撑出 56942 个节点，意味着约 5.7 万次分裂 + 5.7 万次 `malloc`）。预检查完全不碰这部分，所以被摊薄了。

这也解释了上面观察 2 里"插入耗时看不出随 `t` 变快的趋势"：`t` 越大，树高收益越明显，但预检查的相对开销也越大，两条曲线正好抵消了一部分。

用 `-fsanitize=address,undefined -fno-omit-frame-pointer` 重新编译 `perf.c` 跑一遍（`cc -std=c17 -Wall -Wextra -Wpedantic -Werror -O0 -g -fsanitize=address,undefined -fno-omit-frame-pointer btree.c perf.c -o perf_san && ./perf_san`），退出码同样是 0，`btree_verify()` 同样全部通过，没有任何内存错误报告。sanitizer 构建下耗时数字明显更大（`t=2`、10 万个 key：插入 19.45 → 97.82 ms，删除 19.78 → 101.22 ms，都是 5 倍左右），这是 `-O0` + sanitizer 插桩的开销，不代表实现变慢了，性能数字应该以 `-O2`（无 sanitizer）的构建为准。值得对照的是**结构量完全一致**：两种构建下的树高（12/4/2）、节点数（56942/9811/1121）、以及每一条 range query 访问的节点数都逐字相同——耗时会随构建选项和机器状态浮动，结构量不会，它们是算法的性质。

## 常见误区

- **把"阶数 `m`"和"最小度数 `t`"的定义弄混**。不同教材/资料对 B 树的参数化方式不统一：CLRS 用最小度数 `t`（本章采用），另一些资料用"阶数 `m`"（每个节点最多 `m` 个孩子，等价于 `m=2t`，但也有资料把 `m` 定义为"最多 `m-1` 个 key"，等价于 `m=2t-1`）。看到任何 B 树的"阶数是 N"这类描述时，一定要先确认它对应的到底是"最多几个孩子"还是"最多几个 key"，否则套用本章的公式会直接算错上下限。
- **以为删除只有"叶子直接删"和"合并"两种情况**。完整的 7 个分支（1 叶子直接删、2a/2b/2c 内部节点替换前驱/后继/合并、3a/3b/3c 下降路径上借左/借右/合并）缺一不可——只实现"直接删+合并"、跳过"借"，虽然也能维持 key 数下限这条不变量，但会导致合并/分裂发生得远比必要的频繁，退化成很不划算的实现（`fill_child` 里"能借就不合并"的判断正是为了避免这种情况）。
- **合并之后忘记检查 root 是否需要收缩**。如果只在"叶子层"或"内部节点某个非 root 节点"下溢时处理借/合并，却忘了 `btree_delete` 顶层那次额外的 `tree->root->n == 0` 检查，一旦删除操作让 root 恰好清空，就会留下一个 `n=0` 的"僵尸 root"，其唯一孩子实际上应该取代它——这个特判只需要在最外层做一次，不需要在递归内部处理。
- **以为删除的下溢会"向上递归传播"**。很多教材是这么讲的，因为它们描述的是自底向上的实现。本章是自顶向下的：`fill_child` 在**下降之前**就把要进入的孩子补到 `n >= t`，所以下溢永远不会向上传播，也不需要任何回溯机制（详见第 8 节合并图示后面那段）。判断一份 B 树代码属于哪一种，看 `fill_child`/`rebalance` 这类函数是在递归**之前**还是**之后**被调用就行。
- **把 `btree_verify()` 当成"这次操作做对了"的证明**。它只回答"树现在是否合法"。一次不该发生的分裂、一次不该改动的插入、一棵合法但不是你预期的树，它全都放行。本模块四个缺陷都是这么溜过上万次压力测试的——要守住"不该改"这类契约，得用结构指纹逐字节比对操作前后的形状。
- **以为 root 的 key 数下限一律是 0**。叶子 root 可以是 0（空树），内部 root 至少 1——`n=0` 的内部 root 只有一个孩子，是一棵该收缩却没收缩的树。把这两档混成一档，正是本模块修掉的缺陷之一。

## 小结

B 树用"每个节点存多个 key、允许一定范围内浮动"的方式，把二叉搜索树 `O(log2 n)` 的树高压缩到了 `O(log_t n)`，`t` 越大压缩得越明显——这正是它在数据库索引、文件系统这类"每一层都对应一次昂贵 I/O"的场景下比二叉树更常见的原因。插入靠**主动分裂**维持"不超过 `2t-1` 个 key"这条上限；删除靠**借（3a/3b）优先、合并（3c）兜底**维持"不少于 `t-1` 个 key"这条下限，内部节点的删除则先靠**前驱/后继替换（2a/2b）或合并（2c）**把问题转化成子树里的删除，递归到底。插入的分裂和删除的借/合并都发生在"下降之前"，所以两边都不需要向上回溯——这是本实现最值得记住的一条结构性选择。全部 7 个删除分支、root 的增高与收缩，都在 `demo.c`/`tests.c` 里有对应的定向构造和至少一次真实运行验证。

`btree_verify()` 把"这棵树还合法吗"从"肉眼看 `btree_print()` 输出猜"变成了每次操作后都能自动跑的检查——这是本章最有用的一件工具，但它的边界同样是本章的收获之一：**它只检查合法性，不检查"该不该改"**。本模块修掉的四个缺陷全部躲在这个盲区里，其中"重复 key 插入会先分裂再返回 `false`"这一个，在上万次随机压力测试里一直在发生而校验器全程沉默；它的修复第一版还只堵住了两条触发路径中的一条，因为三个回归用例的构造方式恰好屏蔽了另一条。想守住这类缺陷，靠的不是更多的合法性校验，而是**结构指纹**（比较操作前后的完整形状，而不是 `height`/`count_nodes` 这种能一起说谎的聚合量）、**把构造前提写成断言**（显式钉住"root 不满且孩子满"这种必要条件），以及**逐个回退修复来验证用例真的有牙齿**。

3. **修一个真正会通过内存安全检查、但破坏逻辑不变量的 bug**：仿照第 12 节的思路，在 `btree.c` 的一份**拷贝**里故意把 `split_child` 的中点算错（`t` 换成 `t-1` 或反过来），重新编译、跑 `tests.c`，观察 `-Wall -Wextra -Wpedantic -Werror` 和 `-fsanitize=address,undefined` 是否会报错（应该都不会），再观察 `btree_verify()` 驱动的测试是第几个测试、在什么调用栈上第一次抓到这个问题的。做完之后记得恢复原文件，不要把这份改动留在最终代码里。
4. **思考 B+ 树会怎么改**：本章的 B 树把 key 和数据都存在包括内部节点的所有节点里；本项目的 B+ 树主题（`05_b_plus_tree`，由另一部分内容负责）里，所有实际数据只存在叶子节点，内部节点只存"路由用"的 key 副本，叶子之间还会用指针串成一条链表。对照本章的 `split_child`/`delete_from`，想一想："中间 key 被推上去"这一步，在 B+ 树里是"移动"还是"复制"？为什么这个差异会让 B+ 树的叶子合并/借操作比 B 树更简单，却让范围查询变得更容易？
