# 04_b_tree —— B 树：为磁盘而生的多路平衡树

## 本章问题

1. 二叉搜索树每层只能有 2 个分支，如果数据在磁盘上、每次访问一个节点都要一次磁盘 I/O，那"树高"就是"I/O 次数"——B 树用什么办法把树压得更矮？
2. 最小度数 `t` 到底决定了什么？为什么每个节点的 key 数量有"下限"和"上限"，这两个数字是怎么来的？
3. 删除一个 key 的时候，"向兄弟借一个"和"直接合并"是两种完全不同的操作，程序怎么知道该用哪一种？如果要删的 key 恰好在内部节点（不是叶子）上，为什么不能直接删，要先换成前驱或后继？

## 学习目标

- 理解 B 树的核心不变量：每个非 root 节点的 key 数在 `[t-1, 2t-1]` 之间，所有叶子深度相同，且这个不变量是"分裂"和"合并/借"操作存在的唯一原因。
- 亲手实现插入时的节点分裂（split），并看清楚"中间的 key 被推上去"这句话在内存里到底发生了什么。
- 亲手实现删除的全部分支：叶子直接删、叶子下溢后向左/右借、叶子下溢后合并、内部节点删除时替换前驱/后继、根节点收缩。
- 写一个 `btree_verify()`，把"这棵树还是不是一棵合法的 B 树"这件事变成可以在每次操作后自动检查的东西，而不是靠肉眼看 `btree_print()` 的输出猜。
- 亲眼见到一个"分裂中点算错一位"的错误实现是怎么在不触发任何内存错误的情况下,悄悄破坏 B 树的不变量的。

## 数据结构定义

本章采用 CLRS（《算法导论》）的"最小度数 `t`"约定，而不是"阶数 `m`"约定（两者只是同一件事的不同参数化方式，`m = 2t`）：

```c
typedef struct BTreeNode {
    int n;                       /* 当前存了几个 key */
    bool is_leaf;
    int *keys;                   /* 容量 2t-1 */
    struct BTreeNode **children; /* 容量 2t，叶子节点不用 */
} BTreeNode;

typedef struct {
    BTreeNode *root; /* 空树时为 NULL */
    int t;            /* 最小度数，t >= 2 */
} BTree;
```

对最小度数为 `t` 的 B 树（`t >= 2`）：

- 每个非 root 节点至少有 `t-1` 个 key，至多 `2t-1` 个 key。
- 每个非 root 内部节点至少有 `t` 个孩子，至多 `2t` 个孩子。
- root 的 key 数可以少到 0（空树）或 1，但不能超过 `2t-1`。
- 所有叶子的深度相同。
- 节点内的 key 严格递增；对内部节点的第 `i` 个孩子，它子树里的所有 key 都夹在 `keys[i-1]` 和 `keys[i]` 之间（边界情况用 `-∞`/`+∞` 处理）。

**为什么要有"下限"这个东西？** 二叉搜索树的每个节点只装 1 个 key，树高是 `O(log2 n)`。如果把"装多个 key、多个分支"这件事做到极致——每个节点尽量装满、尽量晚分裂——就能用同样的节点数换来更矮的树。但如果不设下限，删除操作可以让节点一直变空而不做任何合并，树会退化回"每个节点 1 个 key"的最坏情况，白白多出很多层。下限保证了"最坏情况下，树高也是 `O(log_t n)`"——这正是 B 树在磁盘等高延迟存储场景下比二叉树快的根本原因：**每一层对应一次昂贵的 I/O，`t` 越大，同样的数据量所需的层数越少。**（本实验用内存里的 `int` key 做教学演示，不涉及真实磁盘 I/O，但节点大小对应磁盘块大小、`t` 对应"一个块能装多少个 key"这套思路是 B 树在数据库、文件系统里的真实用法。）

### 机制剖析：分裂到底在内存里做了什么

`split_child(x, i, t)` 分裂 `x` 的第 `i` 个孩子 `y`（`y` 此时正好装满 `2t-1` 个 key）：

```text
分裂前：              y (2t-1 个 key，装满了)
                      [k0 k1 ... k(t-2) | k(t-1) | k(t) ... k(2t-2)]
                       └── 左半 t-1 个 ──┘  中间   └── 右半 t-1 个 ──┘

分裂后：  x 里插入 k(t-1) 作为新的分隔 key，多出一个孩子指针
          y（原地复用，变成左半） z（新分配，装右半）
          [k0..k(t-2)]            [k(t)..k(2t-2)]
```

具体三步（对应 `btree.c` 的 `split_child`）：

1. **新建节点 `z`**，把 `y` 后半段的 `t-1` 个 key（下标 `t` 到 `2t-2`）复制过去；如果 `y` 不是叶子，还要把对应的 `t` 个孩子指针也复制过去。
2. **`y` 的 `n` 直接改成 `t-1`**——注意这里不需要清空 `y->keys[t..2t-2]`，因为 `n` 已经变小了，那些位置的旧数据永远不会被当作有效 key 读到，下次这个节点再涨到 `n` 个 key 时会被新数据覆盖。这是"逻辑删除"而不是"物理清空"，也是为什么本实验没有在这里做 `memset`。
3. **把中间的 key（下标 `t-1`）搬到父节点 `x` 里**，插入位置是 `i`；同时把新孩子 `z` 的指针插入到 `x->children[i+1]`——插入前要先把 `x` 里下标 `>= i` 的 key 和下标 `>= i+1` 的孩子指针都往后挪一位，腾出空位。

如果被分裂的节点正好是 root，插入前会先检测"root 已经满了吗"，如果满了就先造一个新的空 root、把旧 root 挂成它的第 0 个孩子，再对这个新 root 调用 `split_child(new_root, 0, t)`——这样"root 分裂"和"内部节点分裂"用的是完全同一套代码，不需要为 root 写特殊分支。这也是为什么本实现选择"插入前，如果孩子已满就先分裂"（也叫"下降路径上主动分裂"），而不是"插到叶子后再往上修复"：主动分裂保证递归调用 `insert_nonfull` 时，当前节点一定不满，可以放心往里塞一个 key，完全不用处理"插入之后才发现自己满了，需要往上传递分裂信号"这种回溯逻辑。

## 3. 查找：真实输出

```
========== 3. 查找：命中与未命中 ==========
树结构 (t=3)：
[30 60 90]
  [10 20]
  [40 50]
  [70 80]
  [100 110 120 130]
search(10) = 找到
search(60) = 找到
search(130) = 找到
search(5) = 未找到
search(65) = 未找到
search(999) = 未找到
```

查找的逻辑很直接：在当前节点里从左到右找第一个 `>= key` 的位置 `i`；如果 `keys[i] == key` 就命中；否则如果是叶子就说明整棵树里都没有这个 key，返回未找到；否则递归进入 `children[i]`（因为 B 树的排序性质保证了：如果 key 存在，一定在 `keys[i-1]` 和 `keys[i]` 之间那个子树里）。每下降一层就是一次"磁盘 I/O"（本实验里当然只是一次指针跳转），这正是 `t` 越大、树越矮、查找越快的直接体现。

## 4～8. 删除：叶子层的四种情形

删除是本章真正的难点，一共有 6 种经典情形（4 种发生在叶子层，2 种涉及内部节点，见下面第 10 节的 2a/2b/2c——2c 本质上也是一次合并）。下面固定用同一棵 `t=3` 的树作为起点，一步步删，每删一次都调用 `btree_verify()`：如果任何一步违反了 B 树的不变量，就会立刻看到具体是哪条不变量被破坏——不会等到"看起来很奇怪"才去调试。

### 借（case 3a/3b）的图示

以第 6 节"借左邻居"为例（`t=3`，`fill_child` 里的 3a 分支）：

```text
借之前：       [.. 30 ..]
              /         \
        [10 15 20 25]   [40 50]
         (n=4, 可以借)   (n=2, 触发下溢)

借之后：       [.. 25 ..]
              /         \
        [10 15 20]     [30 50]
         (n=3)           (n=2)
```

分隔 key `30` 被"压"进右孩子（右孩子从 `[40 50]` 变成 `[30 50]`，40 已经在这之前被删掉了，实际看到的是 `[40 50]` 删掉 40 后先补上 30，再删除 40 本身——注意实现里是先补位再删除目标 key，顺序不能反）；左邻居贡献出它最大的 key `25`，顶替 `30` 的位置成为新的分隔 key。整个操作只搬动了 3 个 key（一个从父节点下去，一个从邻居上来，外加叶子内部的位移），没有分配或释放任何节点——这也是为什么"借"比"合并"代价更低，`fill_child` 总是优先尝试借，借不到才合并。

### 合并（case 3c）的图示

以第 8 节为例：

```text
合并之前：   [.. 60 100 ..]
                    /    \
              [80 90]   [110 120]
              (n=2)      (n=2，都在下限，谁也借不出)

合并之后：   [.. 60 ..]
                  \
            [80 90 100 120]
                 (n=4)
```

分隔 key `100` 被拉下来塞进合并后节点的中间，父节点从 3 个 key 减少到 2 个，两个孩子变成一个。如果父节点本身也因此跌到下限以下，这个"下溢"会继续向上传递——递归地对父节点的父节点做同样的借/合并判断，直到某一层不再下溢，或者一直传到 root（root 允许 key 数降到 0，这时树整体收缩一层，见下面第 9 节）。

## 9. Root 收缩：合并一直传到根

上面第 8 节的合并发生在 root 的孩子这一层，root 本身还剩 2 个 key，没有受影响。如果合并之后 root 自己的 key 数也变成 0，会发生什么？专门构造一棵更小的树来只演示这一种情形：

```
========== 9. 专门构造一棵树，强制走一次纯粹的合并 (case 3c) ==========
t=2, 插入 10,20,30,40 之后：
[20]
  [10]
  [30 40]
root=[20]，孩子 [10] 和 [30 40]。

删 40 之后（右孩子降到 [30]，n=1=下限）：
[20]
  [10]
  [30]
  [verify ok after delete 40]

现在删 10：左孩子 [10] 本身就是要删的那个 key 所在的叶子，
删完它会变空（n=0）。它唯一的邻居 [30] 也在下限（n=1），没法借，
=> 必须合并：把分隔 key 20 和右孩子 [30] 一起并入左孩子，
合并后 root 变空，树整体降一层。
[20 30]
height=0（从 1 降到 0，root 从内部节点变成了唯一的叶子）
  [verify ok after delete 10 (pure merge, root shrinks)]
```

关键的一步藏在"删 10"里：删除的目标 key 恰好就在要被合并掉的那个叶子里，所以合并和删除是同一次操作完成的——`merge_children` 把 `[10]`、分隔 key `20`、`[30]` 拼成 `[10 20 30]`，然后再从这个新节点里把 10 删掉，剩下 `[20 30]`。`btree_delete` 在 `delete_from` 返回之后检查一次 `root->n == 0`：如果是，就把这个空 root 释放掉，让它唯一的孩子（这里就是刚合并出来的 `[20 30]`）取代它成为新 root，树高随之减少 1。如果一直合并到 root 的孩子也被合并成了唯一一个、且这个唯一孩子本身也是空的（只会发生在整棵树只剩最后一个 key 被删除的时候），新 root 就是 `NULL`，对应 `btree_height` 返回 `-1` 的空树状态——这在 demo 第 11 节（删到空树）和 `tests.c` 的 `test_root_shrinks_after_merge` 里都有覆盖。这是唯一一处"树的高度会减少"的地方——其余所有借/合并操作都发生在 root 以下，不影响树高。

## 10. 删除内部节点的 key：case 2a / 2b / 2c

前面 5～9 节删的都是叶子里的 key。如果要删的 key 就在**内部节点**上（不是叶子），不能直接从数组里抠掉它——内部节点的 key 同时充当"左右子树的分隔线"，直接删会破坏"左子树全部小于它、右子树全部大于它"这条排序性质，`x->children[i]` 和 `x->children[i+1]` 之间就失去了那条分隔线。正确做法是**先找一个能顶替它、又不破坏排序性质的 key，把这个 key"提"上来，然后把原来的问题转化成"从子树里删掉那个被提上来的 key"**——这样递归下去，最终一定会落到某个叶子上，变成前面已经解决的简单情形。

能顶替的 key 只有两种候选：**前驱**（左子树里最大的 key，一定小于 `keys[i]` 但大于左子树里所有别的 key）和**后继**（右子树里最小的 key，性质对称）。选哪一个，看哪边"借得起"：

```
========== 10. 删除一个存在于内部节点的 key：前驱/后继替换 ==========
case 2a（偷前驱）：插入 20,10,30,5,15 之后：
[20]
  [5 10 15]
  [30]
root=[20]，左孩子 [5 10 15]（n=3，够借），右孩子 [30]（n=1，下限）。
删 20：它是内部节点的 key。检查左孩子，n=3>=t=2，够借
=> 用左子树里最大的 key（前驱，也就是 15）顶替 20，
然后递归地把 15 从左子树里删掉。
[15]
  [5 10]
  [30]
root 现在的 key 是 15（前驱 15 被提上来了）
  [verify ok after delete 20 (internal, case 2a predecessor)]

case 2b（偷后继）：插入 20,10,30,40,35 之后：
[20]
  [10]
  [30 35 40]
root=[20]，左孩子 [10]（n=1，下限，不够借），右孩子 [30 35 40]（n=3，够借）。
删 20：左孩子不够借，看右孩子，n=3>=t=2，够借
=> 用右子树里最小的 key（后继，也就是 30）顶替 20，
然后递归地把 30 从右子树里删掉。
[30]
  [10]
  [35 40]
root 现在的 key 是 30（后继 30 被提上来了）
  [verify ok after delete 20 (internal, case 2b successor)]
```

判断规则（对应 `btree.c` 的 `delete_from` 里处理"找到了要删的 key 但当前节点不是叶子"的分支）：

- **case 2a**：左孩子 `n >= t`（够借）—— 用前驱顶替，递归删前驱。
- **case 2b**：左孩子不够借，但右孩子 `n >= t` —— 用后继顶替，递归删后继。
- **case 2c**：左右孩子都恰好 `n == t-1`（都不够借）—— 干脆把左孩子、要删的 key、右孩子三者合并成一个节点，这个 key 现在"埋"在合并后的节点里，对合并后的节点递归调用 `delete_from` 把它删掉（这时它已经变成了"从一个节点里删 key"的情形，可能继续往下传递）。`tests.c` 的 `test_delete_internal_case2c_merge` 专门构造了两个孩子都恰好 `n == t-1` 的场景来触发这一分支，合并之后树高从 1 降到 0。

无论走哪条分支，"提上来的 key"最终都会被**递归删除**而不是直接从数组里抹掉——这保证了如果递归过程中子树本身也下溢了，借/合并的逻辑照样会被正确触发，不会因为走了"内部节点删除"这条特殊路径就绕过下溢检查。三种情形的共同点：**内部节点的 key 永远不会被"抹除"，只会被替换、搬运，或者和别的 key 一起合并到别处**——它始终留在树里的某个位置，直到真正递归删到某个叶子层，才会发生数组意义上的物理移除。

## 12. 错误示例：分裂中点算错一位，会怎样

前面所有正确演示都反复用到一个数字：分裂满节点时，中间下标是 `t-1`。如果这个 `-1` 被漏掉会怎样？下面这段不是让真正的 `BTree` 跑出错误结果（那样反而会掩盖问题——一棵已经不合法的树后续行为不可预测，没有教学意义），而是在 `demo.c` 里用一个独立的、只有 `n`/`keys[8]` 两个字段的最小结构体单独摆出这个算术错误，纯粹展示"错在哪、错的后果是什么"：

```
========== 12. 错误示例：分裂中点算错一位，会怎样 ==========
满叶子 [1 2 3 4 5]（t=3，最多 2t-1=5 个 key）要分裂。
正确做法：中间下标是 t-1=2，也就是 key[2]=3 被推上去，
左边留 t-1=2 个，右边留 t-1=2 个。

错误版本：把中间下标写成了 t=3（漏了 -1），key[3]=4 被推上去，
左边留 3 个，右边留 1 个。
最少要求每个非 root 节点有 t-1=2 个 key，右边只有 1 个 -> 违反不变量！
这种 bug 不会让程序崩溃，也不会被 sanitizer 抓到（没有非法内存访问），
查找、插入在小规模测试下可能看起来都“正常工作”，直到某次删除因为
某个节点的 key 数比假设的下限还少，触发数组下标或逻辑上的错误。
唯一可靠的防线就是 btree_verify()：每次插入/删除后跑一次，
任何不变量被破坏都会在“案发现场”被抓到，而不是等到很久以后才崩溃。
```

这个例子想说明的是一类**逻辑腐化型 bug**——错误的下标算出来的 `left_n=3`、`right_n=1` 都是合法的数组访问，不会踩到越界，`-fsanitize=address,undefined` 在这里完全无能为力，因为从内存安全的角度看这段代码没有任何问题，它只是"算错了应该算的数"。这种 bug 只能靠**语义层面的不变量检查**（也就是 `btree_verify()` 检查 `n >= t-1`）抓到，而且必须在**每一次**分裂之后立刻检查，因为如果只在最后统一检查一次，出问题时已经经过了很多次后续的插入/删除，`btree_print()` 打出来的树早就面目全非，很难倒推出"到底是哪一次分裂时中点算错了"。这也是为什么本章从 `demo.c` 第 1 节开始，每一次插入/删除之后都紧跟一次 `verify_or_die()`（`demo.c:15` 定义，对 `btree_verify` 的薄包装，失败直接 `abort()`），而不是等演示全部跑完再检查一次。

## 属性校验：`btree_verify()` 具体检查什么

光靠 `btree_search()` 找得到、`btree_count_keys()` 数得对，并不能证明这棵树的**结构**是合法的——一棵严重违反不变量的树完全可能因为"凑巧"而查找结果正确（比如 key 排序没乱，只是某个节点 key 数超了范围）。`btree_verify(tree, err_buf, err_buf_size)`（`btree.c:349`）对整棵树做一次递归遍历（`verify_rec`），逐一检查五条不变量，任何一条不满足就立刻停止并把具体原因写进 `err_buf`：

1. **key 数范围**：`is_root ? 0 : t-1 <= x->n <= 2t-1`。root 允许少到 0（空树）或 1，其余节点必须在 `[t-1, 2t-1]` 之间。
2. **节点内严格递增**：`x->keys[i] < x->keys[i+1]` 对所有 `i` 成立——如果插入逻辑有 bug 导致 key 被插到了错误的位置，这里会立刻抓到。
3. **跨节点的排序边界**：递归下降时把"这个子树允许的 key 范围"作为 `min_key`/`max_key` 一路往下传（第 `i` 个孩子的合法范围是 `(keys[i-1], keys[i])`，边界用 `NULL` 表示 `-∞`/`+∞`），子树里所有 key 必须落在这个区间内——这一条专门抓"分裂/合并/借的时候把某个 key 或子树接错了位置"这类问题，只检查单个节点内部递增是抓不到的。
4. **叶子深度一致**：用一个共享的 `leaf_depth_out` 指针记录第一次遇到的叶子深度，后续每个叶子都必须等于这个深度——一旦不等，说明某次借/合并/根收缩把树"削"得不平衡了。
5. **内部节点孩子指针非空**：`x->n+1` 个孩子指针一个都不能是 `NULL`。

`tests.c` 里几乎每一次 `btree_insert`/`btree_delete` 之后都紧跟一次 `verify_ok()`（对 `btree_verify` 的薄包装，失败时打印错误信息），而不是只在测试函数末尾验证一次——原因和上面第 12 节的教训一致：只有每一步都验证，才能保证"发现问题的那一刻"就是"问题实际发生的那一刻"，而不是隔了几十次操作之后才发现树已经不对了，却无法定位是哪一步出的错。20 个测试里覆盖的构造场景包括 t=2/3/4 度数、60~2000 个 key 的顺序/随机插入、6 种删除分支各自的定向构造、以及 4 组不同 `t`（2/3/5/10）、不同规模（1000~2000 key）、固定种子的随机压力测试（自定义 `xorshift32`，而非 libc 的 `rand()`，保证跨平台可复现）。

## 调试笔记：三次因为"没先验证树的真实形状"而写错的测试

实现 `btree.c` 本身的过程中，`insert`/`split_child`/`delete_from`/`fill_child`/`merge_children` 没有出现过真正的算法 bug——20,000 次随机插入/删除配合每一步 `btree_verify()` 一直是干净的。但在**编写针对具体分支的定向测试**时，连续踩了三次同一类坑，记录下来是因为这类错误本身很有教学价值：

1. **假设错了一棵树的形状**。写 `test_delete_leaf_case3a_borrow_left` 时，凭直觉认为对 `t=2` 的树依次插入 `10,20,30,40,50,60,70` 会得到 `root=[40]`、两个各装 3 个 key 的孩子 `[10,20,30]`/`[50,60,70]`。断言按这个假设写完，一跑就 `FAILED CHECK: t.root->n == 1 && t.root->keys[0] == 40`。真正打印出来的树是 `root=[20,40]`，三个孩子分别是 `[10]`、`[30]`、`[50,60,70]`——插入到 60、70 时是先让 `[50,60,70]` 涨到 3 个 key（`t=2` 时 `2t-1=3`，还没满），而不是像我以为的那样触发另一次分裂。这不是算法错了：在此之前，一个跑了 20,000 次操作、每步都验证的随机压力测试已经证明了核心逻辑没问题。真正的问题是我在写断言之前没有先拿 `btree_print()` 把真实结构打出来看一眼，而是凑了一个"感觉上应该长这样"的形状。修复方式是构造一棵更小、更容易手工验证的树（`{10,20,30,40}`，删 40，插入 5，再删 30），并且**先用一个独立的小程序把每一步的真实结构打印出来确认无误，再去写断言**。
2. **同一类问题在写 case 3b 测试时又犯了一次**，只是这次在写断言之前多了一点警觉——注意到自己并不能确定构造出的场景是否真的触发了"向右借"而不是别的分支，于是主动先用 `btree_print()` 把真实的中间状态打出来，确认了删除 10 之后确实是把根的分隔 key 压进左孩子、右邻居的最小 key 提上来，才把这个过程写进测试文件的注释里（现在 `tests.c` 里那段注释描述的每一步都是照着真实输出写的，不是推测）。
3. **验证了树的形状，但对"前驱被偷走之后还在不在树里"这件事想错了**。`test_delete_internal_case2a_steal_predecessor` 一开始写的是 `CHECK(!btree_search(&t, 15))`，隐含的假设是"被当作前驱抢走的 key 15，删除之后就不存在了"。这是对 B 树 case 2a 语义的误解：前驱 key 只是**从叶子搬到了内部节点**，顶替了被删的那个 key 的位置，它本身依然是树里一个合法、可查找的 key，只是换了个"住址"。跑测试时看到 `[FAIL] test_delete_internal_case2a_steal_predecessor`，才意识到断言反了，改成 `CHECK(btree_search(&t, 15))`（并在旁边写清楚"15 依然存在——现在住在 root 里，不在叶子里了"）。

三次错误的共同教训：**"先用 `btree_print()` 把真实结构打出来看一眼再写断言"** 比"凭对算法的理解直接写断言，跑了再改"更省时间，尤其是在 B 树这种"同一个插入序列，不同的 `t` 会产生完全不同形状"的结构上，直觉常常是错的。这也是为什么整个 `btree.c` 的核心实现反而没有犯过这类错误——它的正确性完全交给了"20,000 次随机操作 + 每步验证"的压力测试去检验，而不是依赖对着某个具体形状的手工推断。

## 设计问题：为什么在下降路径上"主动分裂"，而不是插完再修复

`insert_nonfull` 递归下降时，一旦发现"即将要进入的那个孩子已经满了"，会立刻先对它调用 `split_child`，再继续递归——这被称为**主动分裂**（proactive/eager splitting）。另一种同样正确的实现思路是**先插到叶子，再往上检查是否超限、需要分裂**（类似红黑树插入后再旋转修复的风格）。两种思路都能实现正确的 B 树，本章选择前者，原因是：

- 主动分裂保证了递归调用 `insert_nonfull(x->children[i], key, t)` 时，`x->children[i]` **一定不满**（`n <= 2t-2`），可以放心往里插入一个新 key 而不会超过 `2t-1` 的上限——不需要专门判断"插入后是否超限"。
- 分裂动作永远只发生在"当前节点"和"它的直接孩子"之间，不需要额外的回溯/信号传递机制来通知上一层"你的孩子刚刚分裂了，你可能也需要处理"。
- root 分裂可以被表述为"给 root 找一个新的父节点，再对这个新父节点的第 0 个孩子（也就是旧 root）调用 `split_child`"——完全复用内部节点分裂的同一份代码，不需要为 root 写特殊分支（对比 `btree_insert` 里对 `tree->root->n == 2*t-1` 的检查和红黑树里"根节点重新着色"这类特判逻辑）。

代价是：即使某个孩子分裂之后其实并不需要（比如目标 key 最终插的位置离它很远），也已经执行了一次分裂——但由于分裂只是"一次性地把一个满节点拆成两个半满节点"，均摊下来不会影响插入操作 `O(log_t n)` 的复杂度。

## 性能测试：真实测量数据

`tests.c` 里的随机压力测试关心"结构对不对"，不关心"跑得快不快"。这里单独写了一个 `perf.c`，用 `-O2` 编译（`demo.c`/`tests.c` 为了保留调试信息、方便配合 sanitizer 排错，一直用的是 `-O0 -g`；性能测量要看真实优化后的耗时，所以单独换成 `-O2`），在同一台机器上实际测量三个不同最小度数 `t`（2、8、64）、三种规模（1000、1 万、10 万个 key，随机顺序，`xorshift32` 固定种子保证可复现）下的插入、查找、删除耗时，以及"range query 需要访问多少个节点"——后者是为了给 B+-tree 章节的叶子链表扫描做真实的对比基准（B 树没有叶子链表，做区间查询只能靠中序遍历在内部节点和叶子之间反复上下）。

编译与运行：

```bash

```

1. **`t` 越大，树越矮，范围查询访问的节点越少**：同样 10 万个 key、同样宽度 10000 的 range query，`t=2` 要访问 5706 个节点，`t=8` 降到 983，`t=64` 只需要 121——因为更大的 `t` 让每个节点装更多 key，`log_t n` 直接变小。这就是"I/O 一次装一个磁盘块，块越大越好"这个直觉在真实测量里的样子。

3. **range query 访问的节点数远大于命中的 key 数**（`t=2` 时访问 5706 个节点只为了命中 10001 个 key）：因为大部分被访问的内部节点本身不含目标区间内的 key，只是"路过"去定位叶子——这正是 B+-tree 章节要解决的问题：如果所有实际数据都在叶子、叶子之间又有链表相连，区间查询就只需要定位一次起点、然后线性扫叶子链表，不需要反复经过内部节点。

用 `-fsanitize=address,undefined -fno-omit-frame-pointer` 重新编译 `perf.c` 跑一遍（`cc -std=c17 -Wall -Wextra -Wpedantic -Werror -O0 -g -fsanitize=address,undefined -fno-omit-frame-pointer btree.c perf.c -o perf_san && ./perf_san`），退出码同样是 0，`btree_verify()` 同样全部通过，没有任何内存错误报告——sanitizer 构建下耗时数字明显更大（比如 10 万个 key 的删除从 24.63 ms 变成约 184 ms），这是 sanitizer 插桩本身的开销，不代表实现变慢了，性能数字应该以 `-O2`（无 sanitizer）的构建为准。

## 常见误区

- **把"阶数 `m`"和"最小度数 `t`"的定义弄混**。不同教材/资料对 B 树的参数化方式不统一：CLRS 用最小度数 `t`（本章采用），另一些资料用"阶数 `m`"（每个节点最多 `m` 个孩子，等价于 `m=2t`，但也有资料把 `m` 定义为"最多 `m-1` 个 key"，等价于 `m=2t-1`）。看到任何 B 树的"阶数是 N"这类描述时，一定要先确认它对应的到底是"最多几个孩子"还是"最多几个 key"，否则套用本章的公式会直接算错上下限。
- **以为删除只有"叶子直接删"和"合并"两种情况**。完整的 6 种情形（1 叶子直接删、2a/2b/2c 内部节点替换前驱/后继/合并、3a/3b/3c 下降路径上借左/借右/合并）缺一不可——只实现"直接删+合并"、跳过"借"，虽然也能维持 key 数下限这条不变量，但会导致合并/分裂发生得远比必要的频繁，退化成很不划算的实现（`fill_child` 里"能借就不合并"的判断正是为了避免这种情况）。
- **合并之后忘记检查 root 是否需要收缩**。如果只在"叶子层"或"内部节点某个非 root 节点"下溢时处理借/合并，却忘了 `btree_delete` 顶层那次额外的 `tree->root->n == 0` 检查，一旦删除操作让 root 恰好清空，就会留下一个 `n=0` 的"僵尸 root"，其唯一孩子实际上应该取代它——这个特判只需要在最外层做一次，不需要在递归内部处理。

## 小结

B 树用"每个节点存多个 key、允许一定范围内浮动"的方式，把二叉搜索树 `O(log2 n)` 的树高压缩到了 `O(log_t n)`，`t` 越大压缩得越明显——这正是它在数据库索引、文件系统这类"每一层都对应一次昂贵 I/O"的场景下比二叉树更常见的原因。插入靠**主动分裂**维持"不超过 `2t-1` 个 key"这条上限；删除靠**借（3a/3b）优先、合并（3c）兜底**维持"不少于 `t-1` 个 key"这条下限，内部节点的删除则先靠**前驱/后继替换（2a/2b）或合并（2c）**把问题转化成子树里的删除，递归到底。全部 6 种删除分支、root 的增高与收缩，都在 `demo.c`/`tests.c` 里有对应的定向构造和至少一次真实运行验证；`btree_verify()` 把"这棵树还合法吗"这件事从"肉眼看 `btree_print()` 输出猜"变成了每次操作后都能自动跑的检查，也是抓住本章唯一一批"没写对断言"的 bug（而不是算法本身的 bug）的关键工具。

## 练习

1. **`btree_get_min`/`btree_get_max`**：实现两个函数，返回整棵树里最小/最大的 key（不存在则通过某种方式表示，比如额外的 `bool *found` 参数）。提示：复用 `btree.c` 内部已有的 `find_min`/`find_max` 静态函数的思路，从 root 开始一路走到最左/最右的叶子。

3. **修一个真正会通过内存安全检查、但破坏逻辑不变量的 bug**：仿照第 12 节的思路，在 `btree.c` 的一份**拷贝**里故意把 `split_child` 的中点算错（`t` 换成 `t-1` 或反过来），重新编译、跑 `tests.c`，观察 `-Wall -Wextra -Wpedantic -Werror` 和 `-fsanitize=address,undefined` 是否会报错（应该都不会），再观察 `btree_verify()` 驱动的测试是第几个测试、在什么调用栈上第一次抓到这个问题的。做完之后记得恢复原文件，不要把这份改动留在最终代码里。
4. **思考 B+ 树会怎么改**：本章的 B 树把 key 和数据都存在包括内部节点的所有节点里；本项目的 B+ 树主题（`05_b_plus_tree`，由另一部分内容负责）里，所有实际数据只存在叶子节点，内部节点只存"路由用"的 key 副本，叶子之间还会用指针串成一条链表。对照本章的 `split_child`/`delete_from`，想一想："中间 key 被推上去"这一步，在 B+ 树里是"移动"还是"复制"？为什么这个差异会让 B+ 树的叶子合并/借操作比 B 树更简单，却让范围查询变得更容易？
