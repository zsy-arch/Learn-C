# 01_binary_tree_traversal —— 二叉树遍历全方法

## 本章问题

1. 递归遍历本质上是编译器帮你维护了一个"调用栈"——那用一个数组手写一个栈，是不是就能把递归改写成循环？改出来的迭代版本，凭什么保证顺序和递归版本一样？
2. 递归遍历要 O(h) 的额外栈空间（h 是树高），迭代遍历要 O(h) 的显式栈空间。**莫里斯遍历号称 O(1) 空间**——不用栈、不用递归，它是怎么"记住回去的路"的？
3. 莫里斯遍历会往树里插入一些临时指针（"线索"），如果忘记把这些指针清理掉会怎样？是内存错误，还是别的更隐蔽的问题？
4. 只给你一棵树的前序遍历序列和中序遍历序列，能不能**唯一地**还原出这棵树？为什么"前序 + 后序"通常不行，但"前序/后序 + 中序"可以？

这一章会把这四个问题都做成可以跑起来的实验。

## 学习目标

- 能独立写出前序、中序、后序遍历的递归版本和迭代版本（显式栈），并说清楚迭代版本里栈里存的到底是什么
- 理解莫里斯遍历"借用空指针当线索"的核心技巧，能画出线索建立和拆除的过程
- 知道"线索二叉树"和"莫里斯遍历"的关系：前者是把后者的临时技巧做成持久化的数据结构
- 能用前序/后序 + 中序遍历序列重建二叉树，并解释为什么这个算法依赖"中序遍历里根节点把左右子树分开"这个性质
- 亲眼见到"忘记拆除莫里斯线索"导致的树结构损坏，以及这个损坏在实验里是怎么让 `tree_free` 栈溢出的

## 1. 递归遍历：真实输出

演示树（一棵完全二叉树）：

```text
          4
        /   \
       2     6
      / \   / \
     1   3 5   7
```

```text
========== 1. 构造演示树并做递归遍历 ==========
  前序（递归）: [4, 2, 1, 3, 6, 5, 7]
  中序（递归）: [1, 2, 3, 4, 5, 6, 7]
  后序（递归）: [1, 3, 2, 5, 7, 6, 4]
```

三种递归遍历的代码结构几乎一样，唯一的区别是"访问自己"这一句放在哪：

```c
/* 前序：根 - 左 - 右 */
out[(*n)++] = root->value;          /* 先访问自己 */
preorder_recursive(root->left, ...);
preorder_recursive(root->right, ...);

/* 中序：左 - 根 - 右 */
inorder_recursive(root->left, ...);
out[(*n)++] = root->value;          /* 左子树递归完，回来的时候访问自己 */
inorder_recursive(root->right, ...);

/* 后序：左 - 右 - 根 */
postorder_recursive(root->left, ...);
postorder_recursive(root->right, ...);
out[(*n)++] = root->value;          /* 左右子树都递归完才访问自己 */
```

**为什么中序遍历得到的是有序序列 `[1,2,3,4,5,6,7]`？** 因为这棵树恰好是一棵 BST（左小右大），而中序遍历的定义就是"先输出整个左子树（更小的值），再输出自己，再输出整个右子树（更大的值）"——这不是巧合，是 BST 性质 + 中序遍历定义共同决定的。

## 2. 迭代遍历：栈里到底存了什么

```text
========== 2. 迭代遍历（显式栈），结果应与递归一致 ==========
  前序（迭代）: [4, 2, 1, 3, 6, 5, 7]
  中序（迭代）: [1, 2, 3, 4, 5, 6, 7]
  后序（迭代）: [1, 3, 2, 5, 7, 6, 4]
```

和递归版本逐项比对，完全一致。三种迭代写法的"栈里存什么"是不一样的：

**前序迭代**：栈里存的是"还没访问的子树的根"。

```text
初始: stack = [4]
弹出 4，访问 4，压入 6、2（右先压，左后压，保证左先弹出）
     stack = [6, 2]
弹出 2，访问 2，压入 3、1
     stack = [6, 3, 1]
弹出 1，访问 1（叶子，不压任何东西）
     stack = [6, 3]
弹出 3，访问 3
     stack = [6]
弹出 6，访问 6，压入 7、5
     stack = [7, 5]
... 以此类推，访问顺序 4,2,1,3,6,5,7 —— 与递归前序完全一致
```

**中序迭代**：栈里存的是"当前节点的祖先链（还没访问自己的那些祖先）"，`cur` 指针负责"一路向左走到底"：

```c
const Node *cur = root;
while (cur != NULL || top > 0) {
    while (cur != NULL) {           /* 一路向左，把路上的节点都记下来 */
        stack[top++] = cur;
        cur = cur->left;
    }
    cur = stack[--top];             /* 左边走到头了，弹出最近的祖先 */
    out[(*n)++] = cur->value;       /* 访问它 */
    cur = cur->right;               /* 转向它的右子树，重复"一路向左" */
}
```

这段代码是中序遍历里最容易背错的一段，记忆点是：**内层 while 负责"下潜"，外层每一轮负责"访问一个节点并转向右边"**。

**后序迭代**（本实验用的写法）：这是三种里最麻烦的，因为"访问自己"必须等左右子树都处理完。这里用了一个技巧——**先做"根-右-左"的遍历（这是前序的镜像），再把结果整体反转**，就等价于"左-右-根"：

```c
/* 和前序几乎一样，只是左右压栈顺序反过来（先压左，后压右） */
if (cur->left != NULL) stack[top++] = cur->left;
if (cur->right != NULL) stack[top++] = cur->right;
/* 得到 根-右-左 序列 */
/* ... */
/* 整体反转 -> 左-右-根 */
```

**为什么"根-右-左 反转 = 左-右-根"？** 因为反转一个序列，等价于把"从前往后读"变成"从后往前读"。"根-右-左"倒着读就是"左-右-根"——这是纯粹的序列操作，不需要对着树形状想半天。

## 3. 层序遍历（BFS）

```text
========== 3. 层序遍历（BFS） ==========
  层序: [4, 2, 6, 1, 3, 5, 7]
```

用一个数组模拟队列（`head`/`tail` 两个下标），每弹出一个节点就把它的左右孩子依次推入队尾。这是全书第一次出现"用队列而不是栈"的遍历——**栈（LIFO）产出深度优先序，队列（FIFO）产出广度优先序**，这个对应关系在后面第二章图遍历里会反复用到。

## 4. 莫里斯遍历：O(1) 空间中序遍历

```text
========== 4. 莫里斯遍历（O(1) 空间中序） ==========
  莫里斯中序: [1, 2, 3, 4, 5, 6, 7]
  遍历后树结构与遍历前完全一致？ 是（线索已正确拆除）
```

### 核心技巧：借用空指针当"临时线索"

中序遍历里，一个节点 `cur` 的**中序前驱**是"`cur` 左子树里最右边的那个节点"（一路向左，再一路向右走到底）。普通遍历靠递归调用栈或显式栈"记住"从前驱节点怎么走回 `cur`；莫里斯遍历的想法是：**前驱节点的 `right` 指针本来就是空的（它是左子树里最右的节点，没有右孩子），干脆借用这个空指针，让它临时指向 `cur`**。这样从前驱节点沿着 `right` 走，就能自动"走回" `cur`，完全不需要额外的栈。

```c
if (cur->left == NULL) {
    /* 没有左子树：直接访问自己，然后向右走 */
    out[(*n)++] = cur->value;
    cur = cur->right;
} else {
    Node *predecessor = cur->left;
    while (predecessor->right != NULL && predecessor->right != cur) {
        predecessor = predecessor->right;   /* 找左子树里最右的节点 */
    }
    if (predecessor->right == NULL) {
        predecessor->right = cur;   /* ① 建立线索：借用空指针 */
        cur = cur->left;            /* 先去左子树探索 */
    } else {
        predecessor->right = NULL;  /* ② 拆除线索：恢复原状 */
        out[(*n)++] = cur->value;   /* 左子树已经走完一圈绕回来了，现在访问 cur */
        cur = cur->right;
    }
}
```

以演示树为例，走到节点 `4` 时（左子树是以 `2` 为根的子树）：

```text
第一次到达 4：
  4 的左子树最右节点是 3（路径 4->2->3）
  3->right 是 NULL，说明还没建立线索
  于是：3->right = 4   ← 临时线索，借用空指针
       cur = 2（进入左子树探索）

...（在左子树里正常游走，直到重新走到 4）...

第二次到达 4：
  4 的左子树最右节点还是 3
  3->right 现在等于 4 —— 说明线索已经存在，左子树刚好走完一圈绕回来了
  于是：3->right = NULL  ← 拆除线索，恢复 3 原本"没有右孩子"的状态
       访问 4
       cur = 6（转向右子树）
```

**关键点：线索只是"临时借用"，用完必须物归原主。** 拆线索这一步（`predecessor->right = NULL`）是整个算法最容易漏写的一行，也是本节要重点做实验证明的地方。

### ⚠️ 错误示例：忘记拆除线索会怎样

```c
/* ❌ 危险示例：故意漏掉 predecessor->right = NULL; */
} else {
    /* 这里故意不拆线索 */
    out[(*n)++] = cur->value;
    cur = cur->right;
}
```

真实实验输出：

```text
  ⚠️ 错误示例：如果忘记拆除线索会怎样？
  "错误版"遍历结果: [1, 2, 3, 4, 5, 6, 7]
  遍历后树结构与遍历前一致？ 否（树的 right 指针被永久污染，形状已改变）
```

**遍历结果本身是对的**（`[1,2,3,4,5,6,7]`），这正是这个 bug 最阴险的地方——**光看输出你会以为算法是对的**。但树的结构已经被永久破坏：那些"右子树为空、但左子树非空"的节点，它们的 `right` 现在指向了自己的某个祖先，而不再是 `NULL`。**树里出现了环。**

这不是 UB（不是数组越界或 use-after-free，AddressSanitizer 和 UBSan 都不会报错），而是一个纯粹的**逻辑正确性**问题：指针依然指向合法的、活着的内存，只是指向了"错误的"合法内存。

**这个 bug 有多严重，本实验第一版就亲身体验过：**

写 `demo.c` 的第一版时，破坏完树之后直接调用了普通的 `tree_free(broken_root)`（这是深拷贝出来专门用来做破坏实验的一棵树，不影响原树）。运行结果：

```text
$ ./demo
[... 前面输出正常 ...]
Segmentation fault: 11
```

换成 sanitizer 版本编译后，ASan 精确指出了原因：

```text
SUMMARY: AddressSanitizer: stack-overflow demo.c:41 in tree_free
```

**原因**：`tree_free` 是递归函数，沿着 `left`/`right` 递归释放。但被破坏的树里，某个叶子节点的 `right` 现在指向了它的祖先——于是 `tree_free` 释放完这个"叶子"后，又顺着这个错误的 `right` 指针跑回去释放祖先，祖先又会再一次尝试释放这个"叶子"（这时它已经被 `free` 过了），递归永不收敛，栈很快耗尽。

**修复方式**：既然树已经被故意破坏成带环的结构，就不能再用任何"沿着指针递归"的操作去处理它（`tree_free`、递归遍历、`tree_size` 都不行）。正确做法是**在破坏之前**，先用一次安全的递归（这时树还合法）把所有节点地址记录到一个数组里，之后按地址逐个 `free`，完全不依赖被污染的指针：

```c
/* 树还没被破坏之前，先收集所有节点地址 */
Node *broken_nodes[64];
int broken_node_count = 0;
collect_nodes(broken_root, broken_nodes, &broken_node_count);

morris_inorder_BROKEN_no_restore(broken_root, buf, &n);  /* 现在树里有环了 */

/* 不能再用 tree_free(broken_root)——会栈溢出。按记录好的地址释放： */
for (int i = 0; i < broken_node_count; i++) {
    free(broken_nodes[i]);
}
```

修复后重新编译运行，退出码 0，sanitizer 无任何报错（见下方"编译与运行"一节的真实输出）。**这个从"程序崩溃"到"定位根因"到"修复"的完整过程，就是这一节最想让你亲眼看到的东西：莫里斯遍历的 bug 不会让 ASan 当场报错，但会在后续代码里以完全意想不到的方式（这里是无关的 `tree_free` 栈溢出）反噬你。**

### 大规模验证：莫里斯遍历会不会"用旧了"留下暗伤

`tests.c` 里对一棵 5000 节点的随机树做了两轮莫里斯遍历（`test_large_tree_morris_repeatable`），验证**第二次遍历的结果和第一次完全一样**——如果第一次遍历有任何线索残留，树的形状会被污染，第二次遍历的结果或者树结构对比就会立刻露出马脚。测试结果：两轮遍历、两次结构对比，全部通过。

## 5. 线索二叉树：把"临时"变成"永久"

```text
========== 5. 线索二叉树：把"临时线索"变成"持久线索" ==========
  线索中序遍历: [1, 2, 3, 4, 5, 6, 7]
  说明：叶子节点 1、3、5 的 right 现在是"线索"，分别指向它们的中序后继 2、4、6；
        节点 7 没有中序后继，right 保持 NULL（线索链的终点）。
```

莫里斯遍历里的"线索"是用完就拆的。**线索二叉树（threaded binary tree）**把这个思路反过来：给每个节点加一个标志位（本实验用 `right_is_thread`），永久标记"这个节点的 `right` 到底是真正的右子树，还是指向中序后继的线索"。这样整棵树自带一条"中序遍历链"，查任意节点的中序后继是 **O(1)**，遍历整棵树完全不需要栈、不需要递归：

```c
typedef struct ThreadedNode {
    int value;
    struct ThreadedNode *left;
    struct ThreadedNode *right;
    int right_is_thread;   /* 1 = 线索，0 = 真正的右子树 */
} ThreadedNode;
```

建立线索的过程本质上就是做一次中序遍历，把"上一个访问的节点"记下来，如果它没有右子树，就把它的 `right` 指到"现在正在访问的节点"（也就是它的中序后继）：

```c
static void build_right_threads(ThreadedNode *root) {
    if (root == NULL) return;
    build_right_threads(root->left);
    if (g_thread_prev != NULL && g_thread_prev->right == NULL) {
        g_thread_prev->right = root;
        g_thread_prev->right_is_thread = 1;
    }
    g_thread_prev = root;
    build_right_threads(root->right);
}
```

建好之后，遍历完全不需要栈：

```c
while (cur != NULL) {
    out[(*n)++] = cur->value;
    if (cur->right_is_thread) {
        cur = cur->right;                  /* O(1) 线索跳转 */
    } else if (cur->right != NULL) {
        cur = cur->right;
        while (cur->left != NULL) cur = cur->left;
    } else {
        cur = NULL;                        /* 中序遍历结束 */
    }
}
```

**线索二叉树和莫里斯遍历的关系**：莫里斯遍历是"边遍历边建线索、边遍历边拆线索"，用完就还原成普通二叉树；线索二叉树是"提前把线索建好、永久保留"，代价是每个节点多一个标志位（有些实现甚至不需要额外标志位，用"这个节点原本是否有右子树"的静态信息复用同一个指针，但需要更小心地处理边界）。**如果你的场景需要频繁地"给定一个节点，找它的中序后继"，线索二叉树把这个操作从 O(h) 降到 O(1)；如果只是偶尔完整遍历一次，莫里斯遍历更省心，因为它不改变树的"永久状态"。**

## 6. 从遍历序列重建二叉树

```text
========== 6. 从遍历序列重建二叉树 ==========
  原始前序: [4, 2, 1, 3, 6, 5, 7]
  原始中序: [1, 2, 3, 4, 5, 6, 7]
  原始后序: [1, 3, 2, 5, 7, 6, 4]

  [前序+中序 重建] 重建树的前序: [4, 2, 1, 3, 6, 5, 7]
  [前序+中序 重建] 重建树的中序: [1, 2, 3, 4, 5, 6, 7]
  重建树与原树结构完全一致：是

  [后序+中序 重建] 重建树的后序: [1, 3, 2, 5, 7, 6, 4]
  [后序+中序 重建] 重建树的中序: [1, 2, 3, 4, 5, 6, 7]
  重建树与原树结构完全一致：是
```

**前序 + 中序 重建**的核心洞察：前序序列的**第一个元素永远是当前子树的根**。拿这个根节点的值去中序序列里定位，它左边的所有元素都属于左子树，右边的所有元素都属于右子树——因为中序遍历的定义就是"左子树全部 - 根 - 右子树全部"。定位出左子树有 `k` 个节点后，前序序列里 `[1, 1+k)` 这一段就是左子树的前序序列，剩下的是右子树的前序序列，递归处理即可：

```c
static Node *build_from_pre_in(const int *pre, int pre_n,
                                const int *in, int in_n) {
    if (pre_n == 0) return NULL;
    int root_val = pre[0];                       /* 前序第一个 = 根 */
    int idx = /* 在 in[] 里找 root_val 的位置 */;
    int left_size = idx;
    int right_size = in_n - idx - 1;
    Node *root = node_new(root_val);
    root->left  = build_from_pre_in(pre + 1, left_size, in, left_size);
    root->right = build_from_pre_in(pre + 1 + left_size, right_size,
                                     in + idx + 1, right_size);
    return root;
}
```

**后序 + 中序 重建**是对称的想法：后序序列的**最后一个元素**是根（后序是"左 - 右 - 根"，根排在最后）。区别只是切分前序数组时从头切，切分后序数组时从尾巴倒着切。

**为什么"前序 + 后序"通常不能唯一确定一棵树？** 因为前序和后序都不包含"根把左右子树分开"这个信息——它们各自只告诉你"根排在最前/最后"，但不知道从哪里切开左右子树。只有中序遍历天然带着这个分割点。（如果限定是"满二叉树"或者"每个节点子节点数不是 0 就是 2"，前序+后序才能唯一确定，但那是额外约束，不是遍历序列本身给的信息。）

## 常见错误清单

1. **莫里斯遍历忘记拆线索**：遍历结果可能仍然正确，但树结构被永久破坏，后续任何递归操作都可能因为树里出现环而无法终止（本实验实测：`tree_free` 栈溢出）。—— 详见第 4 节。
2. **中序迭代遍历漏写"转向右子树"**（`cur = cur->right`）：会导致每个节点被访问后立刻死循环在自己身上，或者漏掉整棵右子树。
3. **前序/后序迭代压栈顺序搞反**：前序要"先压右孩子、再压左孩子"才能保证左孩子先弹出；如果压反了，输出顺序会变成"根-右-左"（这恰好是本实验后序迭代法里故意利用的性质，但如果你以为自己写的是前序，那就是 bug）。
4. **重建二叉树时，在中序序列里定位根节点用线性查找**：本实验为了代码简单用了线性查找（对于教学规模的树足够快），生产代码如果树很大、重建很频繁，应该先把中序序列的值建一个哈希表（`值 -> 下标`），把每次定位从 O(n) 降到 O(1)。

## 最佳实践

1. 递归遍历最简单、最不容易写错，没有性能或空间硬约束时优先用它。
2. 需要避免递归栈深度问题（比如树可能退化成很长的链）时，用显式栈的迭代版本。
3. 只有明确需要"额外空间接近 O(1)"、且能容忍"遍历过程中树结构会临时被修改"时才用莫里斯遍历——如果遍历过程中另一个线程或者信号处理函数会读这棵树，莫里斯遍历的临时线索会被别人看到，这是不安全的。
4. 莫里斯遍历里，"建立线索"和"拆除线索"必须成对出现，写完之后一定要写"遍历前后树结构对比"的测试去验证，不要只看遍历结果本身——本节的错误示例证明了"结果对但结构错"是完全可能发生的。
5. 需要频繁查"中序后继"而不是完整遍历时，考虑用线索二叉树把这个操作变成 O(1)。
6. 用前序/后序 + 中序重建二叉树时，记得中序序列是"分割左右子树"的关键，缺了中序序列（只有前序+后序）通常无法唯一重建。

## 练习

1. 用同样的"双栈/反转"思路，能不能写出**不反转数组、只用一个栈**的后序迭代遍历？提示：需要额外记录"上一个访问的节点"，判断当前节点的右子树是不是刚被访问过。
2. 试着给 `morris_inorder` 改一个版本做**前序**遍历（莫里斯前序遍历），想一想"访问自己"这一步应该挪到哪里。
3. 如果给的中序序列里有**重复值**，前序+中序重建算法还能正常工作吗？本实验的 `test_duplicate_values_traversal_only` 只测试了遍历不受重复值影响，没有测试重建——自己写一个实验验证："定位第一次出现的位置"这个策略在有重复值时会不会重建出错误的树。
4. 用 `clock()` 或 `c-algo-experiments/timing.h`（如果项目里有）对比一下：对一棵 100000 节点的随机树，递归中序遍历和莫里斯中序遍历各自的耗时，验证莫里斯遍历"空间省了，但因为要多次遍历左子树找前驱，时间常数变大了"这个说法。
